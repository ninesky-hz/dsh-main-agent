# 命名纪律：一个名字要回答两件事

函数名必须在**不读实现**的前提下让人知道两件事：它会不会改状态，会不会失败。
做不到这两点，读代码的人就得跳到定义去看里面那一行 —— 而这次跳转，是每次、每个人、
每一个调用点都要重复的税。

## 四类动词

**这张表不是白名单的来源。** 真正决定放不放行的是 `tests/naming.test.mjs` 里的
`VERB_CLASSES` 常量 —— 校验规则和被校验对象不能共用同一个可变输入，否则谁都能
往下面这张表里加一个动词来放行违规函数（这版之前就是这么写坏的）。表必须与常量
**逐类双向相等**：多一个少一个都红。表格留在这里，是给人读的同一份事实。

| 类别 | 动词 | 判据 |
| --- | --- | --- |
| 纯读 | `read` `list` `find` `get` `has` `is` `count` `parse` `render` `format` `derive` `resolve` `collect` `compare` `sort` `filter` | 不改任何持久状态；同样输入调两次，看到的东西一样 |
| 幂等写 | `ensure` `apply` `sync` `write` | 改状态，但同样输入再跑一次，结果与第一次相同 |
| 追加事实 | `record` `mark` `append` | 改状态且**不可重复**：每调用一次就多一条，跑两次就是两条 |
| 可被拒 | `request` `dispatch` `require` `reject` | 会失败，而且失败是它的正常结局之一 —— 调用方必须处理 |

幂等写与追加事实要分开，是因为它们对调用方的要求完全不同：前者可以放心重试，
后者重试就会产生重复事实。把两者都叫 `write` / `record`，等于把「能不能重试」这个
问题藏进实现里。

## 两条规则

1. **请求用祈使句，事实用过去式。** `request` / `ensure` 说的是「要它发生」，
   `record` / `mark` 说的是「已经发生过」。名字的时态就是它所在的时刻。
2. **名字必须回答「会不会改状态、会不会失败」。** 做不到就让调用方去读实现 ——
   而调用方不该为了知道这个去读实现。

## 例外表（棘轮基线：只许减不许增）

下面是当前所有**不符合**上述动词前缀的 `export function`，分三组：

- **A** 名词式查询 —— 名字说的是它返回的那份事实（`authorityBasis`、`briefPathFor`）。
  这类名字其实没有撒谎，只是没落在四类动词上。
- **B** 动词不在四类里 —— 它确实会做事（`archiveWorker`、`stripSupervisorLayer`…），只是那个动作
  没被四类动词收进来。
- **C** HTTP 路由处理器 —— endpoint 的入口，不是可复用的领域函数。

这张表的用法是**减法**：下次动到某个函数时，顺手把它改成四类动词之一，然后删掉
它的行。`tests/naming.test.mjs` 会同时检查两件事 —— 源码里新增的不合格名字必须是
表里没有的（否则红），表里留着的名字必须真的还在源码里（删了函数不删行也红）。
所以这张表既不会悄悄变长，也不会留着一堆已经不存在的名字。

一万行、每个调用点都要跟的改造，风险和收益不成比例。先把欠账变成可测的，比拿
