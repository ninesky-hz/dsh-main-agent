一门动手型的课程，从最底层开始

在 DeepSeek Harness 上构建常驻监督者 Agent

十四章，带你从“插件是什么？”一路走到一个真正在跑的 24/7 Main Agent（监督者）—— 它会派生、观察、纠偏并终止 worker 子代理，而且几乎全部是用 harness 已经自带的部分搭出来的。每一章结尾都有一个能在你自己跑着的 dsh web 里实测的东西。

这门课走的是什么路子

你的设计文档（$HOME/src/dsh-supervisor/DESIGN.md 和 $HOME/src/dsh-supervisor/IMPLEMENTATION_PLAN.md） 描述的监督者是“一份 preset 加五个自定义插件”。这门课有意走一条 原生优先的路：复用并配置 harness 已经自带的东西， 保留原生的生命周期机器，只在自带工具无法落实监督者契约的地方， 加一层窄口径的策略前端。这样你到一个能跑的系统会快得多， 而且 —— 对学习来说更重要的是 —— 你配置过的每一块原生部件， 最后都真的被你理解了。

具体说，下面是设计想要的东西，以及 harness 已经提供了什么：

监督者需要什么原生机制（已经在你的 dsh 里跑着）要写自定义代码吗？
派生一个后台 worker原生的可续用子级生命周期，前面套一层受设置保护的 subagent 前端一层薄薄的策略前端
纠偏一个正在跑的 worker原生的追发/冷恢复生命周期；监督者的 send_message 会在运行中回合的下一个模型步骤接上一层薄薄的控制前端
终止一个 workerinterrupt_agent + 之后再也不给它发消息（不再烧一个 token）不用
worker 卡在一个问题上子级原生的 report 工具会唤醒父级；spawn 策略移除了会走到死路的 ask_user_question一处工具限制
worker 做完时被唤醒原生收敛通知；重试耗尽时会补上最终的持久失败原因一个小诊断钩子
按定时器唤醒（耐心等待 / 周期巡检）schedule_create（一行 schedule 服务配置）不用 —— 只是配置
跟踪被锁定的目标原生的目标域与 UI，前面套一层先打底、不阻塞的前端一层薄薄的策略前端
查看 worker 干了什么子级就是 web GUI 里的普通会话，也就是磁盘上的普通 JSONL 文件不用
监督者的人格与协议一份随本仓库打包、已安装且归用户所有的 agent presetYAML + 文字
持久状态（目标、笔记、提问、changelog）.agi/ 里的普通文件，用每个 agent 都有的 shell/fs 工具写不用 —— 只是约定
一眼可看的运行 UI 和真正的停止原生的 view 槽位/投影，加上打包的监督动态 Feed 路由与 Full stop 维护动作打包的 client + 宿主路由
额外的 trace 文件，或者一个无参数的 wait 工具—可选，第 13 章

所以所谓“构建”就是：一份 preset + 一行 schedule 服务 + 一段人格和一套文件约定， 再配上几个窄口径的 goal/spawn/control/diagnostic/UI 策略插件一起打包。worker 生命周期、 重试、持久会话、目标、schedule 和唤醒投递，都仍然是原生的。

为什么在这里原生优先会赢

自定义机器是你在调试 agent 行为之余还得额外调的一堆代码。当 spawn/steer/kill/report 这个循环是 harness 自己的时候，出问题就只可能出在你的提示词或你的 协议上 —— 搜索空间小得多。那些自定义的额外零件，你随时可以后面再加 （第 13 章会具体展示怎么做，用本仓库这个已经装好的 bundle 当模板）。

从一台干净的 PC 开始

  • 不假设你已经有一个 Harness 进程、源码检出、preset、工作区或监督者插件。
  • clone 这门课之后，./tutorial/setup.sh 会装上它的评分器依赖， 并在一个空闲的 localhost 端口上把它伺服起来。它不会把任何 Harness 设置藏起来。
  • 必需的环境准备 会装上 dsh、把 DeepSeek Harness clone 到全课程 都在用的那个路径、配好一个模型、启动 Harness 的 web UI，并创建实验工作区。
  • 不需要 TypeScript 经验。各章里有 TypeScript corner 小框，在你正看着某段语法的时候，正好教你那段语法。

每一章是怎么组织的

  • 先讲道理 —— 用文字讲清概念，然后才是真正的代码。
  • 引用的代码 —— 关于 harness 的每一句断言都指向 $HOME/src/deepseek-harness 里的某个文件（通常还给出行号），好让你自己去核验。代码块会标上 CITED （仓库里确实存在 —— 去读它）或 YOURS （这是你要写进去或贴进去的）。
  • 实机验证 —— 每个里程碑结尾都有一个绿色小框，给出确切的步骤和 预期看到的现象。没通过就别往下走；后面的章节默认它已经过了。
  • 自动评分 —— 每个里程碑框里都有 运行评分器 按钮，以及命令行兜底： "$HOME/src/dsh-supervisor/tutorial/grade.sh" m0…m7 会给持久证据打分（preset 文件、patch 行、.agi/ 状态、会话事件日志），并在 90% 这条线上以 0/1 退出。all 会把 m0–m6 合成一份报告跑；doctor 显示它能看见什么。细节见 $HOME/src/dsh-supervisor/tutorial/GRADING.md。

第 I 部分 —— 理解这台机器（第 1–5 章）

  1. 大局观概念 常驻监督者是什么、“睡/醒”这个循环，以及我们要拼装的原生部件的确切清单。
  2. 从零开始学 Cordis概念 插件、context、服务、inject、事件、effect、waterfall —— 其他一切所立足的那几个想法。还包含你的 JavaScript/TypeScript 起步。
  3. 拆开 harness 看内部概念 profile、bundle、patch 层、两个平面（宿主 vs. preset）、会话日志，以及回合的流转。每种改动该放在哪儿。
  4. 你的实验场动手 逛一遍你刚启动的那套干净部署：进程、$DSH_HOME、磁盘上的会话、web UI，以及安全规则。
  5. Creator mode 与 Cordis 工具集可验证 那个自我指涉的 preset：七个 cordis_* 工具，能检查并且扩展正在运行的运行时。你会定义、运行、然后移除自己的第一个动态插件。

第 II 部分 —— 构建监督者（第 6–12 章）

  1. 里程碑 1 —— 安装并查看 main-agent preset可验证 在它的包行被引用之前先装上这个 bundle、重启、核验生成出来的 preset，并挂载一个真实会话。
  2. 里程碑 2 —— 大脑：人格、协议与 .agi/ 状态契约可验证 读一遍真实装好的 persona/状态契约，并在原生目标服务上测试“先打底工作区、不阻塞”的目标设置。
  3. 里程碑 3 —— 时间：schedule 叠加层可验证 一行 schedule 服务就让会话拥有 schedule_create。耐心等待定时器和周期唤醒，一行自定义定时器代码都不用写。
  4. 里程碑 4 —— worker：派生、纠偏、终止、报告可验证 原生可续用子代理循环，加上受保护的模型/推理强度路由、只向父级提问、下一步纠偏，以及最终失败诊断。
  5. 里程碑 5 —— 监督循环可验证 把收敛通知 + schedule 唤醒 + 会话日志巡检接进完整的“睡/醒/分诊”循环。强制纠偏、强制终止、强制出现一个没人回答的提问。
  6. 里程碑 6 —— UI，最省事的做法可验证 打包的监督动态 Feed 标签页、实时的监督者设置卡片，以及能停掉整条委派运行链的持久 Full stop 控件。
  7. 里程碑 7 —— 验收运行可验证 一个照脚本走的端到端目标，每个行为都强制走一遍，再加一次重启韧性检查。这就是你“做完”的定义。

第 III 部分 —— 超越原生（第 13–14 章）

  1. 可选扩展：真正的宿主插件进阶 当原生不够用时：像你在第 6 章装的那个监督者 bundle 一样，把一个 wait_for_agents 工具、trace 分流器或状态路由打包起来。
  2. 故障排查与参考参考 故障清单、术语表，以及接下来值得读的 harness 文档地图。

关于你已有的那份计划
