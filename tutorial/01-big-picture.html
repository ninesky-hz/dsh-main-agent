第 I 部分 —— 基础

大局观

你正在构建什么、它为什么被塑造成这个样子，以及你将组装起来的各部分原生组件的准确清单。本章还没有代码 —— 它是你接下来十四章里用来导航的地图。

一段话讲清这个产品

一个 Main Agent（监督者）以单个长期存活的聊天会话运行。当你交给它一个任务时，它会 检查工作区的持久状态与相关的 runbook/脚本，写下一个可审阅的目标，武装 原生续行循环，并在同一回合里继续。从那以后它就永远循环： 它带着任务派生一个 worker 子代理，休眠，在 worker 收敛时 （或定时器触发、或你发来消息时）唤醒，巡检发生了什么，然后纠偏、 终止，或派生下一个工作单元。它绝不空等人类：如果你 在耐心窗口内没有回答某个问题，它会记录一个假设并继续。 它知道的一切都存放在磁盘上的纯文本文件里，因此崩溃或重启不产生任何代价。

三种角色

角色是什么落实为
Main Agent（监督者） 那一个长期存活的会话。它做规划、委派、监督，并和你对话。它用自己的工具读取、搜索和核验 —— 它理解自己下的指令，也验收拿回来的东西；只有变更才被委派出去。 与包匹配的 agent preset，名为 main-agent，在第 6 章安装、在第 7 章检视。
Dev Agent（worker） 按工作单元派生的可丢弃专家：浏览器操作员、研究员、实现者。拥有完整工具权限；运行期需要什么就自己装。 一个原生可续行后台 subagent —— 它本身就是一个真实、持久的会话 —— 由随包携带的 subagent 工具启动（第 9 章）。它的角色写在派生提示词里。
你 目标的给出者，也是目标变更、凭据与配置的唯一权威。 在 Web UI 里向 Main Agent 聊天框打字的那个人。所有输入都经由那一个聊天。

心跳：休眠、唤醒、巡检

系统的核心是 Main Agent 在你的消息之间运行的一个循环。现在就把它内化是值得的， 因为后面每一章都在构建它的一部分： 

ensure an armed, reviewable GOAL exists (chapter 7 — goal setup)
loop:
  plan the next unit of work
  spawn a worker with a complete task  (chapter 9 — native subagent tool)
  sleep                                (nothing to do: the turn simply ends)
  wake on ONE of:
    ├─ settle notice: the worker finished — native, unconditional  (chapter 9)
    ├─ report: the worker is blocked on a question — native        (chapter 9)
    ├─ schedule reminder: periodic check-in timer fired            (chapter 8)
    └─ user message: you typed something — that is steering
  triage:
    ├─ worker finished  → read its outcome, record progress, spawn next unit
    ├─ worker blocked   → answer via send_message, or ask you
    ├─ timer fired      → inspect the worker's session; on track → sleep again;
    │                     drifting → steer (send_message); poisoned → kill + respawn
    └─ you spoke        → your word overrides everything
为什么「休眠」是免费的

在这个 harness 里，agent「正在运行」意味着有回合正在执行。回合之间 agent 不产生任何 开销 —— 没有轮询循环，也没有 token 消耗。因此 Main Agent（监督者）通过直接结束回合来休眠， 它被唤醒是因为 harness 往它的收件箱投递了东西：收敛通知、子级的报告、 定时提醒，或你的消息。这四条都是原生投递机制。设计 文档称之为「settle-or-timeout」；你无需写调度器就能得到它。

监督的三个动词

Main Agent 用恰好三个动词管理 worker，三者都是你将在第 9 章遇到的 随包携带的工具：

动词原生工具语义
派生（spawn）subagent（可续行、后台） 创建一个持久的子会话（有它自己的 agent），把任务作为它的第一条消息投递，并立即返回子会话 id。
纠偏（steer）send_message 在一个正在运行的子级下一个模型步骤处加入；空闲的子级会启动一个后续回合，冷子级会从磁盘恢复。只有当当前回合必须立即停止时才先 interrupt。
终止（kill）interrupt_agent + 沉默 停止当前回合。未被发消息的子级不会再做任何工作，也不会消耗任何 token。不存在「销毁」—— 会话仍留在磁盘上，可以检视。

还有一个动词属于 worker：报告（report）。可续行的子级会自动获得 report 工具；调用它会向父级投递一条消息，并且（默认）唤醒父级的 回合。这就是受阻塞时的提问通道：worker 发问、停下，答案通过 send_message 继续 同一个子级。上下文保留，不重启，不分叉。

文件就是事实

Main Agent 的聊天上下文只是缓存；真正的记录是目标工作区里的一堆纯文本 文件，边做边写。这是你设计中的决策 Q2c，它在原生优先的 重写中原封不动地保留下来，因为写文件不需要任何机制 —— 每个 agent 本来就有 shell 与 文件系统工具。 

.agi/
  config.json          # user-only knobs (patience minutes, wake minutes)
  GOAL.md              # written when the native goal starts; reviewable by the user
  GOAL_AMENDMENTS.md   # append-only steering record for active-goal scope changes
  NOTES.md             # the supervisor's free-form working memory
  progress.jsonl       # one JSON line per milestone/insight — your feed
  questions.jsonl      # question stack: pending → assumed/answered/withdrawn
  CHANGELOG.jsonl      # every spawn/steer/kill/assumption, one line each
  subagents/<id>/      # per-worker artifacts (outcome.md at minimum)

第 7 章会把这份目录树变成人格强制执行的契约。因为它们是纯文本文件， 你为它们准备的「UI」就是任何能读文件的东西 —— 包括重启后的监督者 自身，而这正是全部意义所在。

双平面规则（预告）

有一个架构思想支配着你将要做的每一项改动，所以请尽早认识它。运行中的 harness 在两个平面上组合插件：

  • 宿主组合（host composition） —— 每个进程一个实例：注册表、持久化、沙箱、 模型路由、subagent 机制。你只能通过 profile 的 patch 文件触碰它， 而在手动安装路径下，你向它添加一行 schedule 服务。bundle 路径会自动组合 那一行外加它自己的 setup 插件。
  • 一个 agent preset —— 单个会话所贡献的东西：它的工具、它的人格、它的提示词 段落。你编写的东西几乎都在这里。

第 3 章会完整展开这一点；第 6 章应用它。如果你曾困惑「这个 改动应该放哪里？」，答案是：跨会话共享 → 宿主；单个会话的能力 → preset。

第一次任务（最终会到来）

你的设计指定了验收任务：X.com 增长自动化 —— 一个开放式、 长周期、由 worker 操作浏览器的任务。我们不会从那里开始。第 12 章的 验收运行使用一个刻意无聊的目标（「产出一份 docs 目录的摘要， 把工作委派出去」），因为无聊的目标更容易让监督者的失败暴露出来。 任务会变；循环不会变。
