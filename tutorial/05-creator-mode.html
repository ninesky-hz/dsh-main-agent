第 I 部分 —— 基础

Creator mode 与 Cordis 工具集

harness 能在运行的时候读写自己 —— 通过一个 agent 来做。本章介绍 cordis preset（“创造模式”，Creator mode），把它带的七个 cordis_* 工具挨个过一遍，并让你亲手 定义、运行、移除你的第一个活插件。这些本事让你现在就能检查运行时，以后再写出另起名字的 preset 变体。

Creator mode 是什么

cordis 是随附的第四个 preset。它自己的文件头，比任何总结都更能说明它为什么存在：

“A person can ask an agent to author another agent”（人能叫一个 agent 去写另一个 agent）—— 这就是 以后做变体时，这个模式有用的原因。Creator preset 本身，就是 standard 加三样东西：

  • 一行 tool-cordis（包 @deepseek-ai/dsh-tool-cordis）—— 也就是这套工具集；
  • 两个随附的技能：editing-cordis-compositions（写 preset）和 cordis-plugin-development（动态插件）；
  • 一个 persona，它教两平面规则，并禁止修改随附的 preset。
动手之前，必须先知道的文档漂移警告

上面那段注释里写的是 cordis_mount，而 editing-cordis-compositions 技能到现在 还教 cordis_inspect / cordis_mount / cordis_unmount 这几个动词。 这些工具已经不存在了。现在真正活着的那套工具 —— 去唯一的事实来源 packages/extensions/tool-cordis/src/index.ts 里读 —— 注册的是七个工具，走的是 define/run 生命周期。技能里的那套建议（平面、先复制再改、要校验）仍然是对的；过时的只是 工具名。本课程一律用下面这些还活着的名字。

七个工具

每一行都标出了它在 packages/extensions/tool-cordis/src/index.ts 里的注册行号：

工具行它做什么
cordis_inspect_list42列出每一个 inspect provider —— 宿主和客户端上的只读查询面 —— 连同它们的方法和 schema。永远是你第一个要调用的。
cordis_inspect_query61跑一条声明好的只读查询：精确的服务方法（Service.listService）、事件契约（Event.listEvents）、沙箱全局对象（Builtin.listBuiltins）、可见的工具（Tool.listTools），以及 —— 从浏览器这边 —— 活着的 slot 树和主题令牌。
cordis_inspect_self97列出本会话的动态插件；带上 pluginId+packageId 时，返回精确的源码和诊断信息。
cordis_define149记录一个不可变的 package：名字、用途，以及用纯 JavaScript 写的宿主半边和／或客户端半边代码。只校验语法 —— 这时候什么都还没跑。
cordis_run241激活一个 package（第一次用 mode: run；重启、回滚也用它；切换版本用 update）。如果含客户端半边，可能需要在 UI 里由你批准。
cordis_stop330把正在生效的效果拆掉；定义、版本和授权都留着。
cordis_undefine352永久删掉这个插件和它的所有 package。

那套词汇：Plugin → Package → Run

三个 id，出自这套工具自己的系统提示词：

所以一轮迭代长这样：define 出 v1 → run → 发现一个 bug → 在同一个 pluginId 底下 define 出 v2（plugin: {kind: "existing", pluginId}） → 用 mode: "update" 去 run。回滚就是对旧 package 再 run 一次。 版本是不可变的，所以你永远回得去。

动态插件是什么 —— 以及不是什么

  • 它们只活在进程内存里：dsh 一重启就没了。它们不改任何文件，不改 cordis.yml，不改 preset。（README：“Dynamic packages live only in the shared DSH process memory… cannot be promoted automatically.”）
  • 它们是真的：宿主半边能拿到一个通向活运行时的 ctx 门面 —— 可以注册模型 工具、监听事件、调用服务。客户端半边会投递到每一个打开着的网页，并能把 UI 注册进随附的 slot 里。
  • 它们是会话级的：只有定义了某个插件的那个会话，才看得见并控制它。
  • 沙箱“隔离了全局对象，但它不是安全边界” —— 所以才有那条“当成 shell 权限来对待”的立场。 （packages/extensions/tool-cordis/README.md，“Trust stance”。）

换句话说，它们特别适合探查和做原型 —— 第 6 章和第 11 章就是这么用它们的。

TypeScript 角落 · 为什么是“纯 JavaScript”？

动态代码是直接在 node:vm 沙箱里求值的 —— 跑不过任何编译器。TypeScript 的类型标注在这里 会变成语法错误。这对你反而是好事：你在第 2 章学到的东西，一行构建工具都不用就能全部用上。等你在 第 13 章升级成打包插件时，同一份代码会多出类型标注和一个 5 行的构建脚本 —— 差别就这么多。

你的第一个活插件，从头到尾

该你上手了。打开 Web UI → 新建会话 → 工作区 $HOME/agi-lab → preset 创造模式 / Creator mode（也就是 cordis preset）。然后把下面每段 prompt 当成一条聊天消息贴进去，看 agent 怎么做。（你同时在练两样本事：工具的生命周期，以及指挥一个 手里握着工具的 agent —— 你的监督者将来指挥 worker 时需要的，正是同一样本事。）

第 1 步 —— 先发现，再查询

Prompt 1:
  "Call cordis_inspect_list and tell me, in one line each, which inspect
   providers exist on host and client."

Prompt 2:
  "Using cordis_inspect_query, query host Service.listService with no input
   and show me 10 interesting service keys. Then query the exact service
   'agentPresets' and paste its method signatures."

第二条查询返回的是 roster 真实、当下的签名 —— list()、copy()、 standingKeyFor() —— 也就是包的安装流程和以后的 preset 变体所依赖的那套 API。这种 “先发现、再写代码”的纪律是这个技能的标准工作流（第 1–2 步），也正是动态插件很少猜错的原因： 运行时自己会告诉你它的契约。

第 2 步 —— 定义一个宿主半边插件，注册一个真正的模型工具

Prompt 3:
  "Define a dynamic plugin (cordis_define, plugin kind 'new', idPrefix 'lab').
   Host half only, with this code, then run it with cordis_run:

   return {
     name: 'lab-uptime',
     apply(ctx) {
       const started = Date.now()
       harness.registerTool(ctx, harness.defineTool({
         name: 'lab_uptime',
         description: 'Seconds since this dynamic plugin was mounted.',
         parameters: {},
         output: {
           schema: { type: 'string' },
           render(_a, v) { return [{ type: 'text', text: v }] },
         },
         async execute() {
           return `up ${Math.round((Date.now() - started) / 1000)}s`
         },
       }))
     },
   }"

像做第 2 章的练习那样，读一读你自己写的代码：

  • 函数体返回一个插件对象 —— name + apply(ctx)（第 1 个要点）。
  • harness 是一个沙箱内置对象（可以用 Builtin.listBuiltins 发现； 声明在 packages/extensions/cordis-host-runner/src/sandbox.ts 第 18–36 行： harness.handle、harness.defineTool、harness.registerTool(ctx, tool)）。 它的 registerTool/defineTool 这一对，注册出来的模型工具归这个插件的 fiber 所有 —— 所以 cordis_stop 能把它拿掉（第 5 个要点）。
  • parameters: {} 和 output 块对应的是 docs/subsystems/tools.md 里真实的 ToolDefinition 契约：一个描述取值的 schema，加上一个 render， 把取值变成模型能看见的内容。

第 3 步 —— 用它、查它、删它

Prompt 4:  "Call lab_uptime."          → expect: "up Ns"
Prompt 5:  "cordis_inspect_self — show my plugins and their states."
Prompt 6:  "cordis_stop it, try lab_uptime again, and tell me what happens."
           → expect: the tool is gone from the catalog (unknown tool)
Prompt 7:  "cordis_undefine it."
动手试 —— 里程碑：工具集的生命周期

下面这些在你的 Creator 会话里全都观察到过，这一章就算过了：

  1. cordis_inspect_query 返回了 agentPresets 的真实签名。
  2. cordis_define 回了 pluginId/packageId，以及“还没在跑”。
  3. cordis_run 之后，调用 lab_uptime 返回了一个运行时长字符串 —— 一个磁盘上哪儿都不存在的工具，由你写进一个正在运行的进程里的代码提供。
  4. cordis_stop 之后，这个工具消失了（效果被干净拆掉 —— 第 2 章第 5 个要点，现场验证）。
  5. cordis_undefine 之后，cordis_inspect_self 报告说没有任何插件。
这对搭建监督者为什么重要

第 6 章会安装本仓库打包好的那个确切的 preset，这样主路径就不会和提供它那些自定义行的插件版本脱节。 你刚学的 roster 和动态插件机制，仍然是受支持的途径：把那个 preset 复制成一个另起名字的变体， 并对以后的改动做挂载校验。第 11 章会展示同样的宿主/客户端切分，被提升成 bundle 里那个持久的 监督动态 Feed 标签页和设置卡片。

出错了怎么办

  • 运行真的失败了 → 让 agent 调 cordis_inspect_self(pluginId, packageId)：它会返回精确的源码，加上错误和调用栈。 在同一个插件底下定义一个修好的 package；绝不覆盖旧的。
  • 客户端半边显示“等待批准” → 那是在等你：对话里会出现一张批准卡。打一个勾是批准 这个 package；打两个勾是预先批准这个插件将来的版本。
  • service "x" is not declared → 代码用了 ctx.x 却没有声明 inject；改成 ctx.get('x')，或者把它声明出来（技能， “Common failure checks”）。
