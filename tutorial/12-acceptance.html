第 II 部分 —— 构建 · 里程碑 7

验收运行

正式的“做完”定义：一个干净的工作区、一次照脚本走的任务、 每个行为都强制走一遍、每件产物都评分，再加一次重启演练。连着两次 通过，你的监督者才算真的成立。

为什么非要正式验收

第 10 章的演练只证明这些分支在你刚哄过一遍时能工作。验收要证明它们 从冷启动、无人哄的情况下也能工作 —— 这就是演示与系统之间的差别。 下面这份规程就是你设计里的 M6，针对原生优先的实现做了调整。它的退出判据就是你设计里的 那一条：每个步骤连续两次通过；某一步失败时，先修人格的措辞， 再修机器。

准备：一个处女工作区

可选：对着这个工作区打开第 11 章那个终端仪表盘，然后为它开一个全新的 main-agent 会话。从现在起你只说脚本里写好的那几句 —— 不提示、不 说“记得记一笔”。如果你非哄不可，那本身就是一条发现：记下它、改人格、 重跑这次运行。

脚本

每一行：你说/做什么 → 必须发生什么 → 哪件产物能证明它。

#你必须发生证据
1“目标：产出 SUMMARY.md，描述 $HOME/src/deepseek-harness/docs 的目录结构 —— 委派工作、监督、交付。” （关于 SUMMARY.md 放哪儿，一个字都别说。） get_goal → 巡检持久状态与相关 runbook/脚本 → start_goal/GOAL.md → 原生目标被武装，并在同一回合内继续工作。 GOAL.md；UI 里能看到目标；一行进展。
2（什么都不做） 第一个 worker 被派生：任务结构完整、显式给出被允许的模型；结果里写明 路由、模态与生效的推理强度；巡检提醒被武装；spawn 被记录。 聊天里能看到 spawn 的调用/结果；CHANGELOG.jsonl 里一行；schedule_list 显示那条周期提醒；子会话出现在侧边栏。
3（什么都不做 —— 让 worker 跑着，等 ≥ 5 分钟） 定时器唤醒：活性 + 与先前检查点做具体的 report/产物/日志比对。 如果毫无变化，它立刻做一次探针；第二次检查仍无变化就 interrupt 并恢复。 NOTES.md 里一条有实证的检查点或探针记录；绝不是又一次干巴巴的“仍在运行”。
4（被问到输出位置时保持沉默） 提问被记为 pending → 耐心提醒 → 2 分钟后：记为 assumed 并记录那条假设；工作继续。 questions.jsonl 显示状态流转；CHANGELOG 里一行 assumption。
5“让那个 worker 也统计一下 .zh.md 文件。” 通过 send_message 在运行中的 worker 的下一个模型步骤纠偏 —— 不 kill，不重新派生。 CHANGELOG 里一行 steer；这条纠正出现在运行中的子级回合里，并改变了它的方向。
6“那个 worker 跑偏了。终止它，用更紧的任务说明重开。” interrupt_agent → kill 被记录 → 一次新的派生，范围明显收窄。 kill + spawn 两行；旧子级在 list_agents 里处于空闲；新的子会话。
7（什么都不做 —— 让它跑完） 收敛通知被消费；outcome 被读过；SUMMARY.md 交付在假设所说的位置；目标完成；巡检提醒被删除。 SUMMARY.md；最后一行进展；schedule_list 为空；worker 的 outcome.md 位于 .agi/subagents/<id>/。
8“对了 —— 再用一段话提一下 cookbook 子目录。” （在完成之后） 被当作完成后的纠偏：写一条 GOAL_AMENDMENTS.md → 由它自己判断，是开一个小而新的原生目标，还是直接做一次琐碎的编辑 —— 选择要记录。 修正案条目；更新后的 SUMMARY.md。

运行还活着的时候，再加一条“worker 被阻塞”的断言：给某个 worker 一个它确实无法自行 查到的选择。它的工具目录里不能有 ask_user_question；它必须调用 report， 从而在父会话里产生一次 subagent-report 唤醒。用 send_message 回答，必须 能继续同一个子级。

无头驱动（这次运行实际是怎么测的）

这整份脚本你完全可以不碰浏览器就跑完：web 进程把它的 RPC 通过 普通 HTTP 暴露出来 —— POST /api/<method>，信封为 {"type":"client-request","rpcId","method","payload"} （packages/host/apiproxy/src/fetch/handler.ts）。有用的方法： session.create（它会在挂载时校验 preset —— 组合有问题就报 agent-preset-invalid，这是 standingKeyFor 在 API 一侧的替代品）、 session.prompt（mode: queue | steer）、 session.list（每个会话一个 running 标志）、session.history，以及 agentPreset.copy（roster 的创作写入，走 HTTP）。仓库把它们包成 tutorial/drive.py： 

S=$(python3 $HOME/src/dsh-main-agent/tutorial/drive.py create --cwd $HOME/agi-acceptance)
python3 $HOME/src/dsh-main-agent/tutorial/drive.py send  "$S" "Goal: produce SUMMARY.md … deliver."
python3 $HOME/src/dsh-main-agent/tutorial/drive.py steer "$S" "kill that worker and rescope"
python3 $HOME/src/dsh-main-agent/tutorial/drive.py tail  "$S"

重启演练

现在是那个给整套系统命名的性质 —— 对重启无感。你的监督者的 记忆有三层，而且都是持久的：会话日志（原生）、.agi/（你的）、目标 工具的状态（原生）。三层都要证明：

实机验证 —— 重启韧性
  1. 任务进行到一半时（用一个新的目标重跑第 1–2 步，或在第 7 步之前），回到那个跑着 dsh 的 终端，按 Ctrl-C，等它关干净，然后再次运行 dsh web。
  2. 刷新浏览器；打开同一个监督者会话（它就在侧边栏里 —— 会话是 持久的）。
  3. 一字不差地说：“继续。”
  4. 预期：它按需重读 .agi/，用 list_agents 检查它的 worker（持久的子级 —— 已收敛的那个 outcome 就在磁盘上；没做完的那个可以 被发一条消息，从而冷恢复它），如果 worker 仍在运行就重新武装巡检提醒，然后 继续推进。它绝不能重新盘问、重写 GOAL.md，或者为已经做完的工作 再派生一个重复的 worker。
  5. 要诚实核对的一个保留项：本该在进程停着的时候触发的 schedule 提醒， 会在恢复时按 schedule 子系统的补课规则被投递。 打包的监督动态 Feed 和它的停止状态折叠会自动回来；它们不是进程内存里的 动态插件。

Full stop（完全停止）演练

验证这个终端操作员动作
  1. 在一个 worker 正在跑、周期巡检已武装的情况下，打开监督动态 Feed 并点 ■ Full stop（再从某个 worker 的监督动态 Feed 里重复一次，以验证它瞄准的是根谱系）。
  2. 预期活动中的监督者回合和所有被委派的 worker 分支都停下来，并且每一条 schedule 提醒都消失。刷新：停止状态仍在，且没有 worker 还在运行。
  3. 等超过 wakeMinutes：监督者绝不能再次出现。然后你直接发一条提示词； 那次显式恢复只启动监督者；被停掉的 worker 不会自动恢复。

评分与失败台账

给整场运行自动评分："$HOME/src/dsh-main-agent/tutorial/grade.sh" m7 —— 它会针对 $HOME/agi-acceptance 把里程碑 2 到 5 的评分器再跑一遍，然后检查验收特有的 证据（监督者日志里的重启恢复标记、完成之后的 修正案）。只有人能判断的步骤会以 MANUAL 提醒打印出来。 你的 dsh web 带令牌启动时，把令牌一并交给评分器 （--token <t>，或 DSH_TOKEN，或 DSH_URL 里带 ?token=…）， 否则 m6 那几项 HTTP 检查读到的是未认证的 401。

维护一本验收台账（$HOME/src/dsh-main-agent/ 里的一个文件，放在设计文档旁边）：每次运行 每一步一行 —— pass / fail(reason) / coached(what)。设计的退出判据， 原文是：每个步骤连续两次通过。首次运行常见的发现与其修法：

发现类别修法
还没检查目标状态或工作区脚本就先派生了机制回归核验 preset 是否挂载了 dsh-main-agent/goal、没有原生 create_goal，并且要求在 start_goal 之前先 get_goal。
一次 steer 忘了写 CHANGELOG 行协议违反把记录并进该动作自己的句子里：“Steer = send_message + 一行 CHANGELOG，永远一起出现。”
不等就自己把问题答了协议缺口补一句：“你查一眼就能回答的问题不算用户问题 —— 自己解决然后往前走；只有用户才知道的未知项才写进 questions.jsonl。”
定时器到点了，它却去纠偏一个本就在轨的 worker协议缺口补一条明确的默认：“在轨的意思是：最近的工具调用与 Scope 一致。若在轨，除了写 NOTES.md 里的判定，什么都不做。”
worker 卡在 ask_user_question 上干等机制回归核验受保护的 spawn 请求是否带 toolFilter.deny = ['ask_user_question']；作用域为子级的 report 工具必须保留。
spawn 拒绝了某个推理强度策略所选路由没有公示为它配置的固定推理强度。在该模型那一行改选目录里支持的值，或选 provider/default；不要指望它会被截断成能用的值。
工具报错（schedule 不见了、spawn 被拒）机制第 6/8 章的回归：重新校验 preset、检查组合出来的树，并读 dsh web 的日志。

你走到哪儿了

通过这一章，意味着你已经拿到了设计文档所称的无头内核 —— 目标设置、委派、监督、提问、文件、韧性 —— 而它是用一份 preset、一段人格、 一行 schedule、几个窄口径的打包策略插件，以及一套文件约定搭出来的。24/7 的任务现在就是“起 一个更大的目标，让它自己循环”，再加上那个任务需要的任何 worker 工具 —— 而这些工具由 worker 在运行时按自己的任务自行安装。

仍然是可选的东西：计划最初前置的那批自定义机器。如果你想要它 —— 结构化 trace、阻塞式等待，或者超出自带监督动态 Feed 的任务专属 UI —— 第 13 章会展示 打包插件的路径，并用一个真实装好的例子给你当模板。
