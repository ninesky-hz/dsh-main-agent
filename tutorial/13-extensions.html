第 III 部分 —— 超越原生

可选扩展：真正的宿主插件

计划里的 M2 想要的东西全在这儿 —— 工具调用延迟、每个 worker 一份的 trace 文件、一个 阻塞式 wait_for_agents、一个 HTTP 状态端点 —— 而且都是打包好的、能挺过重启的 插件，装进你的 profile 里。你可能永远用不上它们；真要用的时候，这才是老实的做法， 而且有一个真实装好的插件给你当模板。

什么时候该翻到这一章

  • 你希望某个能力挺过重启（动态插件会随进程一起死掉）。
  • 你希望它是进程级的 —— 观察每一个会话，或者对外提供 HTTP。
  • 你已经动态地把它做成了原型（第 5/11 章），而它挣得了永久身份。

工具集自己的文档给出的准则是：「cannot be promoted automatically. To keep an experiment, implement a normal … plugin through the regular development workflow」 （packages/extensions/tool-cordis/README.md）。这一章讲的就是这套流程。

这个仓库已经在用这个模式

监督者项目本身就是这么打包的：$HOME/src/dsh-supervisor/package.json 声明了 dsh.bundle.patch，它的 cordis.patch.yml 插入了 schedule 行，外加一个 setup 插件（lib/index.js，纯 ESM，没有构建步骤），这个插件在启动时把打包的 main-agent preset 装进用户 preset 根目录 —— 端到端验证过： dsh plugin --profile web add file:$HOME/src/dsh-supervisor 同时注册了依赖 和 bundles 条目，而且从“preset 被删掉”的状态重启会自动把一切装回来。在动手写下面的 agi-extras 之前， 先把那三个文件读成最小可用范例；注意， 一个职责是文件系统安装（而不是运行时注册）的插件，理所应当 没有什么需要在销毁时清理。

你装好的模板就是这个监督者 bundle

第 6 章已经把 $HOME/src/dsh-supervisor 装进了 web profile。就拿这个你已经检查过、 并且成功跑过的包当模板 —— 这里不假设你另外检出过任何无关的第三方仓库。

把配方抽出来就是：

  1. 一个 npm 包（"type": "module"，运行时 JS 放在 lib/）。
  2. 把 Harness 的包作为 peer dependencies —— 你的插件 import 它们；运行中的 dsh 提供它们（第 3 章：profile 的模块解析让裸包名解析到那份安装）。
  3. 一份只有一行的 cordis.patch.yml + manifest 里的 dsh.bundle 字段 → 这个包 就是一个 bundle：把它列进 profile 的 dsh.profile.bundles，它那几行就作为 又一层被挂载。
  4. 用第 6 章那套同样的 porcelain 安装： dsh plugin --profile web add "file:$HOME/src/my-plugin"，然后把 dsh 重启一次。 依赖和 bundle-manifest 的改动由这条命令负责；不要手动照抄一遍。
JavaScript 优先 · 没有藏着的构建工具链

这个仓库直接把纯 ESM 放在 lib/ 里发布；它没有 src/、没有 TypeScript 编译器，也没有构建脚本。这个练习就用同样极简的模式。TypeScript 是一种合理的 后续精修，但它需要一套工具链，而你得自己加、自己写文档。

搭骨架：agi-extras，一个包，四个小插件

别做四个包，做一个 —— $HOME/src/agi-extras —— 它的 bundle patch 为每个特性插入一行 （每一行都可被寻址，因此可以在你的 profile patch 里单独禁用）：

把这个仓库的 manifest 复制过来当起点，把包名改成 @agi/extras， 只保留每个文件真正 import 的 peers，把 ./delay、./trace、./wait 和 ./state 分别导出到对应的 lib/*.js，并保留 dsh.bundle.patch 声明。然后 bundle patch 为每个导出的子路径插入一行。下面是每个插件的核心； 定稿之前先读一读它引用的契约。

1 · agi-tool-delay —— 把 waterfall 那一课用上

这个监听器签名是核验过的，不是猜的： 'tools/pre-execute'(exec: ToolExecution, next: () => Promise<PreToolDecision>) — 一个 waterfall，它的监听器返回 allow/deny/ask 的决定，其中「next() delegates to allow」（docs/subsystems/tools.md，第 693 行）。所以“先延迟、再委托” 不过是在返回 next() 之前 await 一个暂停。

2 · agi-subagent-trace —— 把 firehose 那一课用上

它监听提交后追加的那条 feed —— 「'session/event'(session, event)… fire-and-forget; observer failures are logged and contained」（docs/subsystems/session.md）—— 并把子级的工具调用镜像成 可按 worker grep 的文件：

3 · agi-wait —— wait_for_agents，如果你更喜欢阻塞式的手感

用了两个已核验的契约：defineTool（第 5 章；完整参考见 docs/subsystems/tools.md）和 ctx.subagents.listChildren(parentSessionId, signal?)，它的条目是一个带标签的联合类型 —— 子级行是 { kind: 'child', id, activity: 'running' | 'inactive', … }，而损坏的 同级条目会以 { kind: 'diagnostic', id, reason } 行出现，没有 activity 字段（packages/subagent/subagent/src/list-children.ts，第 44–57 行 —— 所以每次读 activity 都必须先检查 kind）。你计划里的一条警告 依然成立：基础层挂载了 dsh-tool-call-timeout-policy，所以要么把它那一行配得比你的唤醒间隔更长，要么 提前返回一句“再叫我一次”。

平面说明：从宿主插件往宿主的 tools 注册表里注册，会让这个工具 处处可见。如果你想让它只属于监督者，就让宿主插件什么都不提供，改在 preset 里加一行 —— 或者接受全局可见；对没有子级的 agent 来说它无害。

4 · agi-state-route —— 用 HTTP 暴露 .agi/

监督者 bundle 已经自带那条有边界的 GET /supervisor/feed?ws=… 路由，供 监督动态 Feed 使用。把这段草图当成另一种任务专属 schema 的练习，而不是当前监督者 还需要的东西。路由契约正是第 3 章那个 web server： ctx.webServer.register({ kind, path, handler }) 返回一个 disposer；重复注册会抛错 （docs/subsystems/web-server.md）。要对 ws 查询参数做路径校验 —— 这个 server 是不鉴权的 localhost。

装进 profile

bundle 层是启动期的事

和你那个被实时监视的 patch 文件不同，bundle 列表是在启动时组合的 —— 所以需要那一次 重启。之后的迭代就是：改 lib/、跑你的测试、重启。把本仓库的测试和 自检习惯照抄过来。要禁用一个 特性而不卸载，就在你的 profile patch 里为它那一行加一条按 id 定位的 disabled: true —— 那部分是实时的。

实机验证 —— 逐个插件
  1. delay：在实验工作区的 config 里设 "toolDelaySeconds": 2；在 .agi 工作区里的会话中，一次工具调用会肉眼可见地滞后约 2 秒（比对会话日志里 tool/call→tool/result 的时间戳）；别处的会话则不会。
  2. trace：派生任意一个 worker；.agi/subagents/<id>/trace.log 会一行一行 写入每一次子级工具调用。
  3. wait：在监督者里说：“派生一个睡 60 秒的 worker，然后调用 wait_for_agents” —— 子级收敛就提前返回；子级耗时长，就在 wakeMinutes 到点时返回。
  4. state： curl -s "http://127.0.0.1:3080/agi/state?ws=$HOME/agi-lab" | python3 -m json.tool
  5. 拆除证明：通过 profile patch 禁用一行 → 它的能力不用重建就消失 （effect 被逐一退回 —— 第 2 章第 5 个想法，在打包尺度上）。

巡视：整个生态是怎么打包 preset 的

dsh-plugin 这个 GitHub topic 是 官方的发现渠道，社区聚合器（带自动刷新索引的 awesome-list； 像 WhaleHub 这样的可视化市场）直接建在它上面。把那个索引里发布 preset 的插件 clone 下来， 能看到三种分发形态，而且都在野外真实存在：

形态例子机制
纯脚本dsh-preset-qa-mode一个 preset 目录 + install.sh/.ps1，把它们拷进 ~/.dsh/.agent-presets/。没有包，没有 bundle。（= 本仓库 scripts/install-manual.sh 那条退路。）
带“启动时拷贝”安装器的 bundledsh-minimal-msys2，以及本仓库dsh.bundle.patch 插入一行插件；这个插件在用户 preset 根目录里没有打包 preset 时就把它写进去。发现过程没有记忆化，所以拷完之后不需要重启；卸载这个插件会刻意留下已安装的 preset 不动。要用 ctx.logger，不要用 console。
bundle 把打包资源注册成根dsh-preset-scaffold它的插件不只是（也不止于）提供一个 preset，而是通过 FileSystemSkillProvider（includeDefaultRoots: false, customSkillDirs）把这个包自己的 skills/ 目录注册成一个 skill 根 —— 它的指导内容会加载进宿主 profile 上的每一个会话，不需要切 preset。当你的贡献是知识而不是组合时，这个模式值得偷。

还见过：roster 支持由部署来配置额外的 preset roots （dsh-agent-presets 的 Config），但 bundle patch 无法往已发布那一行的 config 里追加内容， 除非整份重写一遍 —— 这就是“启动时拷贝”在实践中胜出的原因。monorepo 里还有一种 子路径安装形式：github:owner/repo#ref&path:/.dsh-plugin。

打包的客户端插件（关于 UI 的最后一句话）

这个仓库现在包含了这一章曾经缺少的那个具体生产范例： lib/client.js 注册持久的监督动态 Feed 与监督者设置卡片，而 lib/index.js 提供它们的宿主路由。package.json 声明了 dsh.client.platform: web 并导出 ./client，于是 harness 的 client 模块 扫描就能把它供出来，不需要重建核心前端。只在你的新界面挣得一个永久打包席位时才照抄这个模式； 一次性的实验，就用第 11 章那个已经退役的状态胶囊练习。
