第 II 部分 —— 构建 · 里程碑 2

大脑：persona、协议与 .agi/ 契约

一个监督者，大部分其实是文字。本章读一遍由包装上的那份 persona —— 非阻塞的目标 建立、提问协议、文件纪律 —— 然后测试监督者那个架在工作区之上、接在原生 goal 域上的前端。

persona 住在哪儿、怎么起作用

你 preset 的第一行就是 persona —— 一个提示词段落，它在本 preset 的会话上覆盖掉部署自带的默认值。 它只引用一个按 agent 解析的模板变量 {{model}}：0.2.1 起 loop 只注册 provider 与 model，工作目录不是模板变量，而是由必需的 working-directory 运行时上下文注入。写 {{cwd}} 会让 prompt 在装配期直接失败， 整个 preset 在发出任何模型请求之前就报 unknown prompt variable。

这个 bundle 装进去的是完整协议。先读它，再看下面那张节选示意图。有两条写作规矩告诉你该怎么评价 它 —— 因为 persona 文本是工程，不是感觉：

  • 别去复述基础设施已经保证的事情。不管 persona 提不提，收敛通知都会到；子 agent 的 report 工具本来就在。persona 该管的是决定：这些事发生的时候该怎么办。
  • 每条规则都必须可测。下面每一段，都对得上第 12 章里的一个强制测试。如果你加了一条 逼不出来的规则，你就没法知道它到底管不管用。

状态契约：.agi/

安装页已经按仓库模板把骨架建好了。核实一下；后面跟着 agent 的提示词做事的时候，不要覆盖那份归 用户所有的 config：

文件语义 —— 这就是 persona 会去执行的契约：

文件归谁格式 / 规则
config.json只有你。agent 可以把改动作为问题提出来，但绝不能编辑它。 wakeMinutes：定时巡检的间隔。questionWaitMinutes：等多久之后就自行假设。（原设计里的 toolDelaySeconds 在原生优先的构建里被去掉了；想要的话第 13 章可以把它加回来。）
GOAL.mdagent 在启动原生目标时写它。用户可以查看；它不是一道审批关卡。 目标、约束、里程碑、不在范围内。对进行中目标的范围纠偏写进 GOAL_AMENDMENTS.md，只追加。
NOTES.mdagent。自由形式的工作记忆。按工作需要查和改 —— 没有规定的仪式（设计简化 S1）。
progress.jsonlagent。每个里程碑或关键洞察一行 {"ts","text"} —— 给人看的那条流。
questions.jsonlagent。每个问题一行：{"ts","id","status","q", ...}；status ∈ pending → assumed | answered | withdrawn。
CHANGELOG.jsonlagent。每个有后果的动作一行：{"ts","actor","action","summary","detail"}；action ∈ spawn | steer | kill | assumption | config-proposal。
subagents/<child-id>/agent + 各个 worker。每个 worker 的产物；至少要有该 worker 的 outcome.md。

TypeScript 角落 · YAML 多行字符串

|- 开始一个字面块：换行被保留，末尾那个换行被去掉。装进去的那份结构化协议 之所以读得下去，就是因为它。以后你要改复制出来的变体，每一行都必须比 text: 缩进得更深。

架在原生 goal 域上的非阻塞前端

第 6 章已经换掉了那个面向模型的 goal 配置行。原生的 goal 服务、投影和会话驱动器，都还留在 宿主侧。preset 只禁用了那个“猜意图”的 @deepseek-ai/dsh-tool-goal 前端，换成挂载 dsh-main-agent/goal。它的 start_goal 会写一份规范的 GOAL.md，并且在一次 直接来自人的轮次里、get_goal 之后立刻调用原生服务，然后把控制权交回同一个模型轮。 Web UI 仍然会为这个会话渲染当前目标。那块显示就是你用来替代“进度标签页”的东西，而 progress.jsonl 负责那条流。UI 代码：零行。

一次真实运行的现场笔记（glm-5.3，2026-08-21）
  • 目标轮次是免费的自我续跑。start_goal 一旦武装起原生域，它就会驱动 自动续跑轮（上限由 max_goal_rounds 约束）—— 那个监督者白拿了六轮，可以 反复查它的 worker，然后才交棒给收敛通知和它的巡检提醒。要把它们当成预算来用。
  • update_goal(complete) 需要一次人来发起的轮次，或者一个进行中的目标轮。 被收敛通知唤醒，这两样都不算；那个监督者学会了先把杂事记完，等下一次人的轮次再关闭目标。 你在会话记录里会看到这个套路。
  • 一个命令式的任务也跳不过打底。这个前端没有那个猜意图的 create_goal 工具。续跑守卫要求先做一次当下的 get_goal 检查，并允许在 start_goal 之前做只读检查；操作性工具紧接着就打开了。

先校验，再跑目标建立

装好的 preset 在第 6 章已经做过挂载测试了。在 $HOME/agi-lab 里用 main-agent 开一个全新的会话。

动手试 —— 里程碑 2 验收：非阻塞的目标建立

脚本做完后自动评分："$HOME/src/dsh-main-agent/tutorial/grade.sh" m2 —— 它会核对 .agi/ 骨架、你 persona 里的每一个协议标记、GOAL.md、start_goal 调用、 JSONL 是否合法，以及纠偏记录的纪律。

在一个全新的 main-agent 会话里，由你以用户身份来走这个剧本：

  1. 给一个含糊的任务：“我想要一份 DSH docs 文件夹的整洁、有文档的总结。去做吧。”
  2. 期待它先打底、再动手。它应该先去查目标、持久状态，以及任何相关的运行手册/脚本。 只有当某个实质选择既查不到、又没法用一个安全可逆的假设处理时，它才会问你。
  3. 打底检查：在问答进行到一半时问它“那个 docs 文件夹到底有多大？” 期待：它自己去快速读一下（在 $HOME/src/deepseek-harness/docs 下 ls／数一数），然后用事实回答 —— 它不能拿一个 30 秒就能查清的问题来问你、瞎猜， 或者为它派生 worker。查得到的事实本来就是它自己的活（GROUNDING）。
  4. 期待：start_goal 写出 $HOME/agi-lab/.agi/GOAL.md、 记录下原生目标（在会话 UI 里能看见），并在同一个轮次里接着干活。不应该冒出任何“生成的确认口令”。
  5. 纠偏记录的纪律：说“等等，cookbook 子文件夹也要覆盖。” 期待：GOAL_AMENDMENTS.md 里多出一条记录你这次纠偏的条目 —— GOAL.md 本身没被动过（前后各跑一次 stat -c %Y .agi/GOAL.md 来证明）。
  6. 配置纪律：说“帮我把 questionWaitMinutes 设成 2。” 期待：它拒绝编辑 config.json，改为把这个改动提出来（并记一条 config-proposal）。文件由你自己改。

这时候还不该能用的：耐心倒计时（需要第 8 章的 schedule 工具）和派生（第 9 章）。 如果它试着调 schedule_create 并失败、报“unknown tool” —— 很好，下一章要填的正是这个缺口。

为什么值得对这场问答较真

后面所有东西 —— 任务拆解、worker 提示词、里程碑检查 —— 的质量都是从 GOAL.md 继承来的。 所以建立目标这件事应该有依据，但不能变成一场强制的“第二轮审批仪式”。如果 agent 跳过了已经存在的 自动化，就把 GOAL SETUP 那一段收紧，点名相关的运行手册/脚本类别，然后重新测；persona 反反复复地改 是正常的，也很便宜。

现在有什么了

一个能锁定目标、老实记账、并且拒绝碰不属于自己东西的监督者。它还不会按定时器自己醒来（第 8 章）， 也还不会委派（第 9 章）。
