第 II 部分 —— 构建 · 里程碑 4

worker：派生、纠偏、终止、报告

对你而言 harness 的核心：可续用的后台 subagent。 本章精确讲解这套机器 —— 然后你亲手跑一遍每个动作，这既是 设计里的“M0 冒烟测试”，也是监督循环赖以立足的地基。

可续用的子级究竟是什么

subagent 子系统文档用一句话定义了它，值得读两遍：

把它拆开给监督者看：

  • 子级是一个真实的会话 —— 一份和其它会话一样的持久逻辑 JSONL 日志，能在 web 侧栏看到，也能在磁盘上用 zstd -dc 检视。不是用完即弃的任务。
  • “运行中”只是临时的驻留。当子级有回合要执行时，就存在一个 Activation； 当它完成且名下没有任何待办时，它收敛并卸载。持久会话仍然留着。
  • 冷恢复是免费的。给一个 Activation 已消失的子级发消息，会从它持久化的 会话里把它复活 —— 哪怕是几天后、跨进程重启。除非你主动选择，你的 worker 是不朽的。
  • 一个收件箱，外加一条刻意的纠偏快车道。初始任务与空闲/冷 后续都走原生 FIFO。对一个正在运行的直接子级，本 bundle 的控制前端使用 harness 内置的 Agent.steer()，于是这条纠正会成为当前回合里下一个模型 步骤的输入。

五个动作及其精确语义

1 · 派生（spawn）

插件自有的 subagent 工具接受 { description, prompt, model, run_in_background }。model 是必填的，且必须是 用户所有的 Settings → Plugins 白名单里的一个精确选项。全新安装会 启用 runtime/current，它显式解析本次调用请求所捕获的 provider/model； 固定选项则是精确的 provider/model-id 路由。固定条目会连同原生输入 模态一同呈现（[text] / [text,image]），因此监督者可以把 图像类工作路由给用户已批准的、具备视觉能力的 worker。设置为空则禁用派生； 没有任何路由会被隐式继承。每条被允许的模型路由都有自己的推理强度设置： provider/default 不发送显式推理强度，而固定推理强度 id 必须由所选模型 自我声明。即便是 runtime/current，也只跟随主请求的模型路由，绝不跟随其 推理强度。工具结果会显示生效的路由、输入模态 与推理强度。插件始终通过原生 SubagentRequest.agentOptions 转发解析后的路由。在后台模式下它调用 ctx.subagents.startContinuable()：

还有几个事实一并生效。子级会在自己的头部把监督者记为 parentSession （血统是持久的）。该行的 persona 会注册为子级自己的人格，甚至 快照进它的描述符以供冷恢复（docs/subsystems/subagent.md：“a continuable descriptor … additionally snapshots resolved child agentOptions.provider/model and optional persona/toolFilter”）。而 插件自有的 toolFilter 会移除 ask_user_question，而子级作用域的原生 report 工具仍然可用。最后，该工具立刻返回子级 id —— 派生从不为工作阻塞。当有显式推理强度生效时，插件会预留该 id，并 把这个推理强度写进子级第一条持久请求的头部。

2 · 纠偏（steer）—— send_message

空闲、等待中与冷子级仍由原生投递表负责：

监督者的 preset 只替换面向模型的那一行控制项。对一个活着的、正在运行的直接子级， dsh-supervisor/control 调用 Agent.steer()，也就是 web UI 的纠偏动作所用的同一个原语：消息在下一个模型步骤加入，不必等整个回合结束。 其它所有状态都回落到原生 followup()。只有当当前回合本身必须停下时，才用 先 interrupt 再 send。直接父级的权限被完整保留。

3 · 终止（kill）—— interrupt_agent + 沉默

这里刻意没有 destroy。Kill = interrupt + 永不再发消息：一个不再收到消息的子级 不再执行任何回合、消耗零 token，而它的会话留在磁盘上供事后剖析。“Kill” 在你的 changelog 里，指的就是这两个决定的组合。

4 · 报告（report）—— worker 那一侧

每一个可续用的进程内子级都会自动获得 report 工具 —— 不是你的 preset 加的；而是 host 平面的 tool-subagent-report 行注册了一套 continuable-child 设置， 把它安装进每一个子级（packages/bundle/base/cordis.patch.yml，第 331–333 行； cordis preset 的注释解释了为什么那一行必须位于宿主平面）。投递方式的默认值是 wakeup：父级会得到真实的一个回合。这就是你的「被阻塞问题」通道，而你的 worker 人格（第 6 章）已经要求 worker 使用它。这条受保护的派生请求还会在 schema 与执行两个层面拒绝全局 ask_user_question 工具：在那里打开的提问 只会在子级会话里静静等待，而且不会发出 subagent-report。

5 · 收敛通知 —— 免费的唤醒

无条件。你派生的每个 worker 完成时都会恰好唤醒你一次 —— 并附上它的最终 消息。当重试耗尽时，bundle 会用子级持久的最终 turn/end 来充实这同一条被认领的通知，产生诸如 Terminal failure [QUOTA]: … 这样的文本。中间的可重试失败保持静默；如果某次重试 成功了，这条通知就是普通的。子级仍可通过 send_message 被恢复。

记账 —— list_agents

枚举你的子级，状态为 running / idle / ready （ready = 仅存在于存储、可恢复），读取持久状态而不唤醒任何 人（docs/tool-catalog.md、list_agents；服务： subagent.md 里的 listChildren()）。监督者就是这样检查有哪些驱动器 开着，并执行由设置掌控的 worker 上限。“运行中”不是有进展的证明。 一次巡检必须把一份报告、产物/日志变更或已完成的步骤，与先前的 NOTES.md 检查点做比对。

任务提示词：契约中属于监督者的那一半

原生机器负责投递消息；消息写着什么是你设计里第 7.2 节的结构， 如今完全由派生调用承载（简化项 S4 —— 不再有 brief 文件）。角色随任务 需要而定 —— 实现者、浏览器操作员，尤其还有 explorer：一种 worker，其全部 交付物就是一份报告（勘察这个仓库、测绘这个系统），当监督者自己快速阅读 不够用时，它就是监督者的远程眼睛。你在第 7 章写的人格已经强制要求这套 结构；下面是一次好的派生该有的形状，供你后面的测试使用：

实机验证 —— 手工跑一遍 M0 冒烟测试

在信任监督者去驱动之前，你先以用户身份亲手驱动每一个动作。使用 $HOME/agi-lab 里的 main-agent 会话。这就是设计里的「五个观察」M0， 已按你的工具做适配。

里程碑 4 验收 —— 五个观察

自动评分："$HOME/src/dsh-supervisor/tutorial/grade.sh" m4 —— 读取会话事件日志 并核验五个观察都留下了持久证据（spawn/steer/kill 调用、 subagent-settled 与 subagent-report 消息、子级的一次 report、outcome.md）。

  1. 派生会返回一个 id。说：“在后台派生一个 dev agent 做一个慢任务： 角色 researcher；目标：用 bash 睡 90 秒，然后统计 /tmp 里的文件数；协议 照常（outcome.md + report）。” 预期：工具结果给出一个已启动的子级 id；监督者的回合结束。侧栏里出现一个新的子级会话；磁盘上， find "$HOME/.dsh/sessions" -name session.jsonl.zstd | wc -l 的结果加一。
  2. 纠偏落在下一个步骤。趁子级在睡，说：“纠偏一下：除了文件， 也统计目录。” 预期：发生一次 send_message 调用；在 子级的会话视图里，这条纠正被接进正在运行的回合，并影响 下一个模型步骤；worker 不必先跑完它的旧计划。
  3. 收敛通知唤醒父级。等子级完成。预期： 监督者自己醒来并带有一条通知（“子级如何结束” + 最终摘要）， 读 outcome，并记录进展。你什么都没做。
  4. report 唤醒父级。派生第二个 worker，其任务被刻意 写得欠明确（例如“把问候语写到配置好的位置”，而 Context 里 没有任何位置，并明确指示这不可自行发现 —— 要求通过 report 来问）。 预期：子级调用 report 提出一个精确的问题；监督者 醒来，通过 send_message 作答；子级把答案当作自己的下一个 回合，随后完成。
  5. interrupt 止住燃烧。派生第三个 worker 跑一个长任务，然后说： “那个跑飞了 —— 终止它，并记下这次 kill。” 预期： interrupt_agent；随后 list_agents 显示它不在运行（idle/ready）； CHANGELOG.jsonl 里落下一行 kill；它的会话日志里 不再出现新的子级活动。

另外核验人格是否生效：在 UI 里打开第一个子级的会话 —— 它的行为 应当体现你那一行里的 Dev-Agent 人格（例如最后会报告一段 摘要）。如果子级表现得像一个通用编码 agent、从不报告，那么你 dev 派生行（tool-spawn-dev）上的 persona: 块有缩进问题 —— 请重新校验该 preset。

为什么第 2 个观察比它看起来更重要

飞行中途纠偏，本是你原设计以为必须靠 kill + fork 自行构建的 能力。这个小小的控制前端复用了 harness 已有的步骤边界纠偏原语， 保住了上下文，并把空闲/冷投递留给原生子系统。

现在有了什么

监督的每个机械部件都能在你手下跑通：派生、纠偏、终止、报告、收敛、 枚举。剩下的就是让监督者无人值守地、按自己的时钟驱动它们 —— 也就是那个循环。
