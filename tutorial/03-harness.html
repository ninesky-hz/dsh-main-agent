第 I 部分 —— 基础

拆开 harness 看内部

一个运行中的 dsh 是怎么一层层拼出来的；会话和 agent 住在哪里； 所谓“一轮（turn）”究竟是什么；以及对你最重要的那条 —— 判断一处改动该落在哪个平面的两平面规则。

从零到一个跑起来的产品：分层

一个运行中的 dsh 就是一棵很大的 Cordis 插件树，而这棵树是在启动时，把一串排好序的补丁层 叠加到一个空列表上组装出来的。没有任何东西是写死的；连“这个产品”本身，都只是分层的产物： 

[]                                  ← the profile root: literally an empty list
 + @deepseek-ai/dsh-base            ← bundle: model adapters, tools, persistence,
 |                                     sandbox, subagent machinery, jobs, goals ...
 + @deepseek-ai/dsh-web-app         ← bundle: the browser application
 + profiles/web/cordis.patch.yml    ← your profile override layer
 + ~/.dsh/cordis.patch.yml          ← home-level patch layer (if present)
 + --patch overlays                 ← command-line extras

每个概念，精确地说：

  • profile（配置档）是 $DSH_HOME/profiles/<name> 下的一个目录，里面放一个 package.json（说明要叠哪些 bundle，以及树外的插件依赖），还有你自己的 cordis.patch.yml。模板 web 和 headless 会自动初始化。 （出处：packages/boot/app-boot/README.md，“Profiles”。）
  • bundle是一个 npm 包，它的 manifest 里声明了 "dsh": { "bundle": { "patch": "./cordis.patch.yml" } } —— 也就是一整套可分发的一串 配置行，外加这些行所挂载的代码。
  • patch（补丁）按 id 定位到某一行并整块替换它的配置，或者 insert 出新行。 你 profile 的补丁文件是被实时监听的：改完不用重启，整棵树就会重新组装。 （同一出处：“Every profile boot keeps cordis.patch.yml live through watchUserPatches.”）

想看你机器启动时最终组装出来的整棵树，有专门的 dump 命令（只读，安全）：

dsh --profile web --dump-config

它打印出来的任何一行，都可以用你自己的补丁替换或禁用。就这一句话，就是 harness 全部的“配置 API”。

冲突规则，完整版

一个 preset 行如果发布一个服务却没有 isolate realm，那它就是进程级全局发布的 —— 于是第二个挂载这个 preset 的会话就会和第一个撞上。preset 的挂载器会直接拒绝这种写法， 而不是留到以后再炸，报错信息里会点名是哪个服务。修法你在第 2 章见过（把 provider 和消费者 包进同一个 isolate 组）；实际结论更简单：保留从 standard 继承来的那些组。 打包好的 preset 就是这么做的，第 6 章会用两个会话来验证。

Agent preset：每个会话自己选组装方式

preset是一个目录，里面有一个 agent.cordis.yml（配置行）和一个 preset.yml（显示名、描述）。你在 Web UI 里开会话时选一个 preset；roster 就为这个会话挂载 那套装组。随部署出厂的有四个 —— standard、code、minimal、 cordis（Creator mode）—— 它们就放在安装目录旁边；本地自己写的则放在 $DSH_HOME/.agent-presets/<id>/ 下。

有个服务叫 roster（ctx.agentPresets），负责 preset 的发现、编写和校验。 包的安装流程就是用它装上 main-agent 的；下面这些动词，以后写变体也用得上：

为什么用 copy()，而不是从零手写 YAML

“A composition written from scratch usually forgets a group realm or a consumer row; a copy starts loadable”（editing-cordis-compositions 技能）。copy() 还会校验 id、把副本落到这次部署所配置的可写根目录里，失败时回滚。本仓库已经把成品 preset 一起发了出去， 这样它的配置行就不会和插件版本脱节。你要写变体的话，就用这套 API 把装好的 main-agent 复制成一个新 id。

走进一个会话：日志、轮、步

现在把镜头拉近到一个正在跑的 agent。三个名词就撑起了全部：

  • session（会话）是一份只追加的持久事件日志（user/message、 assistant/message、tool/call、tool/result、turn/start……）， 外加一个头部（工作区 cwd、父系血缘、创建时间）。它在磁盘上就是一个如假包换的 JSONL 文件 —— 第 4 章你会亲手打开一个。
  • step（步）是一次模型请求，加上这次请求引发的那些工具调用。
  • turn（轮）是零个或多个 step：有输入被认领时开启，不再欠任何东西时关闭。

由此推出两条规则，你的监督者设计正是靠它们撑着：

  • 模型能看见的，就一定记进了日志。任何进入模型请求的东西，都必须能从会话日志里还原出来 —— 这是一条运行时不变量。也正因如此，一个子 agent 的全部行为，事后光靠它自己的日志就能查， 这正好原生替代了原方案里自定义的 trace.log。
  • 输入只从一个收件箱进来。一个 agent 只有一个 FIFO 收件箱；每一条消息 —— 你发的、定时提醒、子 agent 的报告、收敛通知 —— 都会变成一轮，而且顺序是可观察的。 “休眠”就是收件箱为空；“唤醒”就是来了一次投递。没有别的调度器。

工具流水线（策略住在哪儿）

当模型要求运行一个工具时，这次调用会走一条带关卡的流水线 —— 全是 waterfall，全都可以由插件扩展： 

tools/pre-execute   → allow / deny / ask / transform / delay   (policy seat)
guards              → monotonic checks
tools/execute       → around-dispatch wrappers (timeouts live here)
tools/post-execute  → inspect or replace the result
tools/result        → the immutable outcome

当前的 bundle 只在很窄的范围内用了这个策略位：它的 goal 前端会先拦住操作性工具，直到一次长时间运行的 续跑已经查过原生 goal 状态、看过相关的工作区材料、并且把 start_goal 架好为止。第 13 章里那个 可选的工具延迟插件是另一个例子（docs/tool-execution-pipeline.md）。同一条流水线也解释了 Web UI 里的沙箱/审批提示 —— 那是内置的 pre-execute 策略在请你做决定。
