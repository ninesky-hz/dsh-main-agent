第 II 部分 —— 构建 · 里程碑 1

安装并查看 main-agent

这是第一个构建动作。你把本仓库作为一个 dsh profile 的 bundle 装上、重启一次， 它随包携带的第二份 bundle patch（presets/main-agent.patch.yml）就会声明 preset-main-agent 这一行，roster 里随之出现 Main Agent（监督者）。等这个包真的存在了，你再去查看那些 名字形如 dsh-main-agent/… 的配置行。

依赖顺序

clone repository                         (setup page)
  → dsh plugin add                       (package becomes profile dependency)
    → restart dsh web                    (bundle rows compose at boot)
      → bundle patch declares the preset (presets/main-agent.patch.yml registers
                                         preset-main-agent → main-agent appears)
        → preset subpath rows resolve    (goal/control/spawn mount)
          → start and test a session

把中间那两步调换顺序，就会得到本章专门要防的那个报错： Cannot find package dsh-main-agent/control 或 dsh-main-agent/spawn。YAML 里的配置行不是 npm 的安装指令；它指向的包必须已经能从 profile 里解析出来。

第 1 步 —— 确认干净的前置状态

test -f "$HOME/src/dsh-main-agent/package.json"
test -f "$HOME/src/dsh-main-agent/agent-presets/main-agent/agent.cordis.yml"
test -f "$HOME/.dsh/profiles/web/package.json"

# On the clean course path this should print no supervisor dependency yet:
grep -n 'dsh-main-agent' "$HOME/.dsh/profiles/web/package.json" || true

如果机器其实并不干净、$HOME/.dsh/.agent-presets/main-agent 已经存在，而你又想要这个包 当前那份 preset，那就在安装前先把它挪开。安装器的 legacy 拷贝在默认的 syncPreset: if-absent 模式下，绝不会覆盖用户自己的那份。

同样要检查的是手工挂过的 preset bundle：早期迁移期有人会手写一个 @local/dsh-main-agent-preset 之类的包并把它加进 profile 的 dsh.profile.bundles。那样一来这个 profile 里就有了两条指向同一个 preset id 的声明行，而重复的声明行不会报错、也不会去重（后一层获胜），选择器里的文案会安静地变成 另一份。本仓库的安装是自足的，安装前请把这类手工 bundle 从 profile 依赖里摘掉。

第 2 步 —— 安装 supervisor bundle

两条等价路径，只选一条。发布版（0.10.0 起，本包改名为 dsh-main-agent 并迁到新仓库）直接用 git URL 安装： 

dsh plugin --profile web add https://gitee.com/n-sky/dsh-main-agent.git

或者用你刚克隆下来的本地仓库（本章课程路径）： 

cd "$HOME/src/dsh-main-agent"
dsh plugin --profile web add "file:$PWD"

0.9.4 及以前的版本发布在旧仓库 https://gitee.com/n-sky/dsh-supervisor.git（现已冻结）；无论从哪个 URL 安装，依赖键与目录名都取自包清单的 name，所以装出来一律是 node_modules/dsh-main-agent。旧版装过的 profile，请用新 URL 重装一次并 摘掉旧的 dsh-supervisor 依赖键与 bundle 条目。

就这一条命令，会更新 profile 的依赖和有序的 bundle 列表。不要在 dsh profile 里跑 npm install，也不要手工编辑它的 package.json。包管理器可能会打印 peer 依赖警告，因为那些 peer 是 Harness 从它自己的安装里提供的；用下面那道“安装关卡”来区分无害警告和 真正的失败。

回到跑着 dsh web 的那个终端，按 Ctrl-C，等它退干净，然后运行： 

dsh web

这次重启是必须的，因为 bundle 列表是在启动时组装的。启动过程中，这个包会挂载它自己的 settings/feed 宿主插件、原生 schedule 服务，并让 presets/main-agent.patch.yml 里那条 preset-main-agent（@deepseek-ai/dsh-agent-preset）行注册 preset —— 这一条才是 0.2.x 上让 preset 出现在选择器里的东西。它由 scripts/sync-preset-patch.mjs 从 agent-presets/main-agent/ 生成， 同步关系由 tests/preset-patch.test.mjs（npm test）把守；改了预设源文件 就重跑 npm run sync-preset 再提交。

同一个 setup 插件还会把包里带的 main-agent 目录复制进 $HOME/.dsh/.agent-presets/（目录不存在时）。这是为更老的 dsh 保留的路径： 0.2.x 起宿主已经不再读取那个目录，所以它现在不是 preset 的来源。

第 3 步 —— 证明包、bundle、preset 三者都在

安装关卡 
grep -n 'dsh-main-agent' "$HOME/.dsh/profiles/web/package.json"
dsh --profile web --dump-config | grep -E 'agi-schedule|agi-supervisor-setup'
# The two files below are the compat copy for older dsh — they prove it was written:
test -f "$HOME/.dsh/.agent-presets/main-agent/agent.cordis.yml"
test -f "$HOME/.dsh/.agent-presets/main-agent/preset.yml"
# This is what makes the preset exist — it must print exactly one line:
dsh --profile web --dump-config | grep -c 'preset-main-agent'
dsh --profile web --dump-config | grep -A4 'id: preset-main-agent'

这些命令必须全部成功。前两条 test -f 证明的是兼容副本已被写入 （那是给更老的 dsh 用的）；preset 是否真的生效要看声明行： preset-main-agent 的计数必须是 1，紧接着的 name: 必须是 @deepseek-ai/dsh-agent-preset、其 config.name 为 Main Agent（监督者），而且这一行没有 disabled:。在浏览器里，Settings → Plugins 里还必须有 Supervisor。任何一项没过，就停在这儿别往下走。

第 4 步 —— 查看这个包装进来的那些行

用只读方式打开 $HOME/src/dsh-main-agent/agent-presets/main-agent/agent.cordis.yml —— 声明行 preset-main-agent 的 config.plugins 就是这份文件的逐行副本 （tests/preset-patch.test.mjs 保证两者一致；.agent-presets/ 里那份兼容副本 内容相同）。那些关键的策略替换已经做好了：

现在验证那些“绕过”都不存在：

grep -nE 'subagent_fork|@deepseek-ai/dsh-tool-goal' \
  "$HOME/src/dsh-main-agent/agent-presets/main-agent/agent.cordis.yml" || true

这条命令应该什么都不打印。让那三个自定义名字能被解析出来的包导出，在 $HOME/src/dsh-main-agent/package.json 里能看得到，也就是 ./goal、 ./control 和 ./spawn。它们背后的生命周期后端仍然是原生的；这几个前端额外 加上了有依据的目标、下一步纠偏，以及由设置项掌管的模型/推理强度策略。

第 5 步 —— 挂载一个真实会话

Web UI → 新建会话 → 工作区 $HOME/agi-lab → preset Main Agent（监督者）。启动它，然后问： 

List every tool you can currently call, names only, grouped by theme.
里程碑 1 验收

自动评分： "$HOME/src/dsh-main-agent/tutorial/grade.sh" m1 --ws "$HOME/agi-lab"

  1. 会话能启动，没有 Cannot find package 那种挂载错误。
  2. 工具里有 subagent、send_message、interrupt_agent、 list_agents、get_goal、start_goal 和 update_goal。
  3. subagent_fork 和原生的 create_goal 都不在。
  4. 同一个 preset 上的第二个会话也能启动，这证明没有哪个 preset 服务漏进进程级全局域。
手写 preset 仍然适用的地方

第 2–5 章教的 Cordis 和 roster 机制，已经够你写一个变体出来了。但在本课程的主路径上，用打包好的 preset 才是可复现的构建：它不会和提供这些行的插件版本脱节。你以后要真做变体，就通过 roster 把 main-agent 复制成一个新 id，改那份属于你的副本，再用 standingKeyFor 给它做挂载校验。

现在有什么了

一个能完整挂载的监督者 preset、它那套归包所有的策略前端、活着的设置项、Feed 路由，还有 schedule 服务。第 7 章会去读并测试装好的 persona 和持久状态契约。
