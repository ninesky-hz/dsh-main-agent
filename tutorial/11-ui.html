第 II 部分 —— 构建 · 里程碑 6

UI，最省事的做法

你的设计里画了两个自定义标签页。这一章先看其中有多少 现成的 Web UI 已经免费送给你了，然后再走一遍 bundle 现在真正交付的那一件 —— 监督动态 Feed 视图标签页、实时生效的 Supervisor 设置，以及那个持久的 Full stop（完全停止） 控件 —— 它能终结整场被委派的运行。

现成的 UI 本来就有多全

把你设计里的两个标签页，映射到此刻屏幕上的东西：

设计中的功能现成的等价物
进展标签页：被锁定的目标 + 修正案目标工具的状态，由 Web UI 按会话渲染（第 7 章）。GOAL.md / GOAL_AMENDMENTS.md 在任何编辑器里都能读。
进展标签页：事件流.agi/progress.jsonl —— 一条 tail -f 的距离（见下）。外加监督者自己的聊天，它会把里程碑讲出来。
进展标签页：提问栈.agi/questions.jsonl，同样处理 —— 而待答的问题也会出现在聊天里，你在那里回答它们。
Subagent 标签页：运行列表侧边栏里该工作区的会话列表：每个 worker 都是那里的一条会话，最新的在最前。
Subagent 标签页：详情面板 + 实时 trace点开那个 worker 的会话：完整对话、每一次工具调用与结果，实时流式呈现。这比 tail 一段 trace 严格更好。
Subagent 标签页：kill/steer 按钮按设计，所有输入都流过 Main Agent（监督者）的聊天（你的 Q18）：“kill the researcher” 就是那个按钮。聊天就是控制面板。

所以诚实的差距很小：一个扫一眼就知道“监督者现在在干什么”的视图，以及 读文件流的便利。打包的 bundle 现在用一个自带的 监督动态 Feed 标签页把两样都补上了 （见下）；而终端里的习惯，仍然是同一份持久状态的一个有用的独立视图。

自带的监督动态 Feed 标签页（bundle 装了什么）

从 v0.2.0 起，dsh-main-agent 包自带一个持久的客户端插件：打开任意 会话，视图环（装着 Chat 和 Trajectory 的那一圈标签页）里就多出一个 监督动态 Feed 条目。对于带 .agi/ 目录的工作区，它一次把整场运行 渲染成一眼可读 —— 目标卡片（实时，来自原生 goal 投影）、worker 及其 outcome.md、进展时间线、带 answered/assumed 徽章的提问栈、 动作 changelog、notes，以及任务报告。

  • 浏览器那一半 —— lib/client.js，一个手写的惰性 CJS 工厂 （window.__ModuleLoader__.load…，即 docs/cookbook/adding-a-settings-card.md §Packaging 里记录的格式）。它把 id supervisor-feed 注册进自带的 conversation.view 列表槽位 —— 是加法， 绝不替换 Chat。由 client-modules 扫描自动提供：该包声明了 dsh.client {platform:'web'} + exports["./client"]，于是页面拿到 /plugins/dsh-main-agent/client.js，前端无需重建。
  • 宿主那一半 —— GET /supervisor/feed?ws=<workspace>，在 lib/index.js 里：一个注入了 webServer 的嵌套 fiber 读取 .agi/ 目录树（文本有上限，JSONL 只留尾部），因此无头的 profile 仍然能原封不动地装上 preset 安装器。
  • 数据仍然原生优先 —— 目标来自 useProjection('goal')，worker 来自 subagent.list RPC，只有 .agi/ 里的文件走 这个包自己的路由。
实机验证 —— 里程碑 6 验收

自动评分："$HOME/src/dsh-main-agent/tutorial/grade.sh" m6 —— 核验已安装的 客户端那一半、__DSH_BOOT__ 那一行、被提供出去的 bundle，以及 feed 路由。 你的 dsh web 带令牌启动时，把令牌一并交给它 （--token <t>，或 DSH_TOKEN，或 DSH_URL 里带 ?token=…）—— 否则这几项读到的是未认证的 401。然后是肉眼环节： 打开你的 main-agent 会话 → 点视图环里的 监督动态 → 目标卡片、 worker、进展时间线都在，并在刷新（约 5 秒），同时 ■ Full stop 在监督者活动期间可用。

Full stop（完全停止）：停住整个循环，而不只是一个回合

原生的停止方块只中止当前回合。而周期性的 worker 巡检是持久的，所以它 还能再次唤醒监督者。监督动态 Feed 头部的 ■ Full stop 控件瞄准的是根 main-agent，即使你是在某个 worker 的监督动态 Feed 里点的。如果根会话是冷的，浏览器会 恢复那个已存在的会话而不启动新回合，然后 POST /supervisor/stop?session=… 中止 活动中的工作、等待空闲、递归释放每一条常驻的可续跑 worker 分支、进入 该 agent 的独占维护窗口、删除所有活动的 schedule 提醒，并再次 刷写持久化。worker 在会话历史里仍然可见，但它们不再运行、也不再上报。

GET /supervisor/stop?session=… 会把活着的或冷却下来的持久状态折叠起来，所以“已停止”这个状态 能熬过刷新。之后你直接发一条提示词，就是显式恢复监督者；它不会自动重启 那些被停掉的 worker，而当工作再次被武装时，Full stop 按钮又会变得可用。

元配置卡片（Settings → Plugins → Supervisor）

从 v0.4.0 起，bundle 还通过原生设置域自带了监督者的 元配置：命名空间就是这份组合里本插件的入口 id agi-supervisor-setup（不是包名），含 workerModels（白名单，带一个 默认的 当前运行时模型 下拉选项，以及若干固定路由 —— 它们显示原生的 [text]/[text,image] 模态标签和模型自报的推理强度）、 workerEfforts（每条允许路由一个由用户掌管的 provider 默认值，或目录中明确公示的推理强度； Main Agent（监督者）永远不能自己选、也不会继承它）、 maxParallelWorkers（由 spawn 工具在调用时硬性执行）、 wakeMinutes（监督者多久醒一次去巡检 worker），以及 questionWaitMinutes（等答案等多久，超时就记下一条 假设然后继续）。在 UI 卡片里编辑它，或者直接编辑当前 profile 的 patch 层 ~/.dsh/profiles/<profile>/cordis.patch.yml 里 - id: agi-supervisor-setup 那一行的 config —— 卡片写的就是同一行、同一份 带修订围栏的文档。~/.dsh/settings.yaml 是已移除的旧格式： 启动时宿主会把它改名成 settings.yaml.imported 并逐节尝试写回，节名必须 正好是运行中的入口 id 才会生效，所以旧写法里的 dsh-supervisor: 块只会 留下一条 was not imported into entry … 警告。模型清单就是 完整的策略：受保护的 subagent schema 只暴露那些确切的选项、强制要求显式给出一个， 并在清单为空时直接消失。runtime/current 解析的是发起这次调用所捕获的 路由，绝不是会话创建时那份过期的路由；不存在隐式兜底。 推理强度会针对确切解析出的路由做校验，绝不截断、也绝不悄悄降级。 一切都是实时生效的：模型清单一变，插件就重新挂载那个 schema；每次调用都重新校验 设置；而 SUPERVISOR META-CONFIG 这段系统提示词是一个文本 函数，每次请求都重新渲染进去。两个值得抄走的实现 事实：一个刚派生出来的可续跑子级，在它第一个回合之前会报 activity: 'inactive'， 所以诚实的并发上限执行，需要在活动计数之上再加一本“正在启动”的账；还有，spawn 工具声明了 isConcurrencySafe: false，于是同一回合内的两次派生会串行地过这道检查。

可选的客户端插件练习：一个状态胶囊

这个练习保留下来是为了教动态 host/client 插件，但它不属于当前的 产品或里程碑验收。持久的监督动态 Feed 在 v0.2.0 取代了这个进程内存里的胶囊。

现在是那点花活 —— 顺便也是学客户端动态插件的借口。Web UI 的布局 专门为这类追加声明了一个横跨整帧的浮动层：

“状态胶囊就该放这儿” —— 这份目录字面上就点了你的用例。这个胶囊会通过一个包私有的宿主方法 轮询你的 .agi/ 文件（宿主那一半用 harness.handle， 客户端那一半用 host.call —— 也就是 cordis-plugin-development 技能里 记录的那座 RPC 桥）。

在一个 Creator 模式会话里（$HOME/agi-lab），先让它真去查一下那个槽位 （cordis_inspect_query、client、Slots.listSubTree、根 shell.overlay —— 必须有一个浏览器标签页开着才能回答），然后再定义并运行这个分成两半的插件：

拿你写的代码去对技能里的规则 —— 每一条都在这里出现了：

  • 宿主那一半用 harness.handle 暴露一个 JSON 方法；客户端用 host.call 调用它。跨越边界的只有纯 JSON（我们先解析/切成标量）。
  • 客户端用 React.createElement —— 动态代码里不能有 JSX。
  • 定时器是 timer 服务，硬注入，而 ctx.interval 返回一个 销毁函数，由 useEffect 交还 —— 在 stop/update 时安全拆除。
  • 槽位是在 slots.inject(…) 内部注册的，用一个全新的 id，于是它加在 自带条目旁边，并按 overlay 契约选择加入 pointerEvents。
  • 文件系统访问走 ctx.get('fs') —— Cordis 服务，而不是 Node 全局 （沙箱不给这些）。它的读动词已核实： readText(target, signal?)“把整个常规文本文件读成一个解码后的字符串” （packages/fs/fs/README.md，服务表）。
可选练习的检查

这一项不由 m6 检查；当前的评分器查的是打包的监督动态 Feed 与那些路由。

  1. cordis_run 对客户端那一半返回 awaiting-approval → Creator 会话里出现一张 批准卡片 → 批准它一次。
  2. 胶囊出现在 Web UI 的右下角，每一个打开的标签页里都有。
  3. 追加一行，看它在约 5 秒内变化： echo '{"ts":"now","text":"pill test"}' >> $HOME/agi-lab/.agi/progress.jsonl
  4. 往 questions.jsonl 里加一行假的待答问题 → ❓ 计数出现；把它的 状态改成 answered → 计数清掉。
  5. cordis_stop → 胶囊在各处消失（两端的效果都拆干净了）。 再跑一次 —— 一次批准就够了（授权是持久的）。

记住它的天性：动态插件随进程一起死。如果你爱上了这个胶囊， 第 13 章会讲“把它提升成真插件”意味着什么；在那之前，重启之后重新跑它， 在任何 Creator 会话里都只是两次工具调用。

这段历史练习教的是什么

host/client 桥、加法式槽位注册、拆除安全的定时器，以及纯 JSON 边界， 正是打包的客户端插件所用的同一批概念。生产版监督者把它们用在持久的 conversation.view 监督动态 Feed 里，而不是每次重启后都要再来一个动态插件。
