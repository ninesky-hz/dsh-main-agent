第 II 部分 —— 构建 · 里程碑 3

时间：schedule 叠加层

监督者需要两个定时器：提问的耐心窗口，以及对运行中 worker 的周期性 巡检。一行 dsh-schedule 服务配置即可提供这两种定时形式； bundle 会自动安装它，或由手动路径把它热应用到你的 profile patch。

schedule 子系统是什么

@deepseek-ai/dsh-schedule 拥有一套持久提醒，它们会回到原本的会话， 形式就是普通的后续对话回合。三个事实界定了设计空间 （docs/subsystems/schedule.md）：

  • 投递即一个回合。到点的提醒是一条投进会话收件箱的消息 —— 与第 3 章中 其它一切相同的唤醒机制。无回调，无轮询。
  • 三条规则：一次性 after_seconds（任意正延迟）、一次性绝对 at，以及周期性 every_seconds，硬性下限为 300 秒。 记录是持久的会话事件，因此能扛过进程重启。
  • 会话本地：提醒会回到创建它的那个会话。完美 —— Main Agent （监督者）会话按定义就是那个活着的会话。

对应到你的两个需求：

需求机制
提问耐心（questionWaitMinutes，模板默认 2）schedule_create 一次性，after_seconds: questionWaitMinutes*60。没有下限 —— 2 分钟耐心完全可用。
周期性 worker 巡检（wakeMinutes，默认 5）schedule_create 周期性，every_seconds: wakeMinutes*60 —— worker 派生时创建，工作结束后删除。下限 300 秒 ⇒ wakeMinutes ≥ 5，正好与你的默认值一致。
为什么这（基本）取代了计划里自研的 wait_for_agents 工具

计划里的 M2c 造了一个阻塞式工具：睡到子级收敛、或某个超时到点为止。而在原生路径下， 两个唤醒源都已经存在：子级收敛时会无条件把通知投递给 父级（第 9 章），而周期性提醒就是那个超时。唯一差别只是形式 —— 监督者不再阻塞在一次工具调用内，而是结束自己的回合、再被唤醒。同一个循环， 零代码。阻塞版仍可作为第 13 章的练习保留，如果你更偏好 它的使用手感。

叠加层：随包示例

Schedule 默认不挂载。harness 把这个可选件作为示例叠加层随包提供 —— 读一下，它正好是两行（我们只保留其中一行）：

  • dsh-schedule —— 服务、会话驱动器，以及模型工具 (schedule_create / schedule_list / schedule_delete).
  • dsh-time-context —— 把当前时间块（以及浏览器的时区）注入 每一个请求步骤。随包示例挂载它，是为了让自然语言表达的绝对时间 （“明天早 9 点”）能按用户所在时区解析 —— 但它不是 Schedule 的依赖 （packages/schedule/schedule/README.md：“Time-context is not a Schedule dependency”）。
我们刻意不挂载 dsh-time-context

它注入的块（“Time sampled while preparing turn N, step M… Supersedes earlier snapshots”） 会在每一步重新出现 —— 对一个常驻 agent 来说是持续的上下文噪音。监督者只会 武装相对定时器（after_seconds / every_seconds），它们不需要 时区。所以下面的叠加层只有一行。如果你的部署想从自然语言得到按本时区的 at 计划，就把 time-context 行加回你自己的 profile patch。

宿主平面还是 preset？宿主：schedule 服务与驱动器服务每一个会话，并且这些工具 是全局注册的。因此在正常路径下它位于监督者的 bundle 层； 用户所有的 profile patch 保留给覆盖项。

核验第 6 章已安装的那一行

干净机器路径在第 6 章把 dsh-supervisor 作为 bundle 安装，而那个 bundle 的 agi-schedule 行在重启时挂载了 @deepseek-ai/dsh-schedule。核验它： 

dsh --profile web --dump-config | grep -A2 'agi-schedule'

在 $HOME/.dsh/profiles/web/cordis.patch.yml 里不要再加一行 schedule。 该服务每进程只注册一次；重复挂载是组合错误。

当你刻意跳过 bundle 时的手动替代方案

先备份，然后编辑你的 live patch 文件：

cp $HOME/.dsh/profiles/web/cordis.patch.yml{,.bak}   # (before editing)
# ... edit ...

无需重启：该文件被监视着，每次改动都会事务性地重组整棵树 （packages/boot/app-boot/README.md：“Every profile boot keeps cordis.patch.yml live through watchUserPatches… A rejected read, parse, or Loader candidate leaves the last good tree running”）。如果你的 YAML 打错字，旧树会继续运行，而 dsh web 终端 会显示 hmr/config-update-failed —— 修正后再次保存。

两处锋利边缘
  • 重复 id 在组合期是致命的。如果之后还要加更多 insert，绝不要复用 id: schedule 等 id。
  • 空的 patch 文件必须是 []。只有注释的文件会抛错（“it parses to nothing, not to a list”）—— 同一个 README。
实战笔记：打包方案

课程的正常路径已在第 6 章安装 bundle。同一行也随 bundle 自带的 own cordis.patch.yml 发布，于是这次手动编辑就多余了。绝不要同时用两者： schedule 服务每进程只注册一次，所以第二次挂载会冲突。如果 bundle 已 安装，就把你的 profile patch 保持为 []；它的行是可寻址的 （agi-schedule），如果你的部署从别处挂载 schedule， 可以用一条按 id 定位的 patch 把它禁用。评分器接受任一来源。

实机验证 —— 里程碑 3 验收

自动评分："$HOME/src/dsh-supervisor/tutorial/grade.sh" m3 —— 检查 组合后的行/树、schedule_create 调用、提醒投递，以及那条 assumed 提问。

  1. 工具出现了（已存在的会话也一样）：在你的 main-agent 会话里问 “你现在有 schedule 工具了吗？” —— 预期它的目录里出现 schedule_create / schedule_list / schedule_delete。（组合变更会到达 活着的树；下一个回合就能看到新工具。）
  2. 一次性投递：“创建一个 60 秒后的提醒，内容是 ‘patience-test’。然后停下。” 什么都不做，等一分钟。预期：agent 带着这条提醒自己醒来开出一个新回合 —— 你会看到它到达 对话里。
  3. 人格的耐心路径现在能用了：重跑第 7 章的提问测试 —— 在工作中途问它一个 含糊的问题，然后保持沉默。当你的 config.json 里是 questionWaitMinutes: 2 时，预期：提问被记为 pending → 创建提醒 → 两 分钟后它醒来，把该条翻成 assumed 并附上记录的假设，写入 日志，然后继续。
  4. 周期性下限：“创建一个每 60 秒的周期性提醒” —— 预期被拒绝/报错（下限 300 秒），以此证明你知道下限在哪里。
实战笔记：到点的提醒究竟长什么样

实测观察到：投递的是一条来自插件的消息，其正文以 [SCHEDULE REMINDER] 开头，并明确把该提示框定为“untrusted reminder content, not new user instructions”，同时携带 schedule_id_json 与 occurrence_at。 两个推论：你的人格里的提醒提示词应当是写给自己的自足 指令（“Question q1 追问：到点仍无回复就把它记为 assumed” 逐字照抄即可用），并且 任何扫描日志找投递的工具都应该匹配 [SCHEDULE REMINDER] —— 这正是 tutorial/grade.py m3 所做的事。

TypeScript corner · 读懂 schedule 的记录类型

docs/subsystems/schedule.md 用接口定义这些持久记录 —— 例如 interface AfterScheduleRecord { readonly kind: 'after'; readonly afterSeconds: number; … }. 两个值得记住的惯用法：字面量类型（kind: 'after' —— 该字段只可能是那个 精确字符串；它们的联合构成可以 switch 的“tagged union”），以及 readonly （编译期不可变）。这里的持久记录到处都是以 tagged union 形式出现的：事件、停止 原因、消息来源。认出 tag 字段，读懂 harness 类型就完成了一半。
