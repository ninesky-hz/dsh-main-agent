第 I 部分 —— 基础

从零开始学 Cordis

harness 的口号是「一切都是插件」。本章讲解它底下的插件框架 —— Cordis —— 讲到当你日后阅读一个真实插件时，每一行都有意义的程度。它还会顺带教你一路上需要的 JavaScript 与 TypeScript。

为什么非要有插件框架？

想象用寻常方式构建一个 AI agent 产品：一个大程序，模型客户端、 工具注册表、会话日志和 UI 全都互相 import。每增加一项能力都意味着 修改核心。DeepSeek Harness 拒绝这种做法：不存在需要打补丁的特权核心。模型 适配器是插件。工具注册表是插件。agent 循环本身就是插件。你 通过在其它插件旁边再挂载一个插件来扩展产品，通过卸载它来移除你的扩展 —— 其它东西一概 不变。

Cordis 就是让这一切可组合的框架。harness 把它内嵌进来（一份锁定版本的副本位于 $HOME/src/deepseek-harness/vendor/cordis/），它的入门文档把整套东西浓缩成五个 想法。下面是直接引自 harness 文档的原文，然后逐条拆解：

就这样。一个插件就是一个模块（或对象），它暴露 name 与 apply 函数。当框架挂载这个插件时，它只调用一次 apply(ctx)， 并交给它一个上下文 —— 这是插件窥视其它一切的窗口。当插件被 卸载时，它通过那个上下文注册的一切都会被自动清理 （想法 5 解释其原理）。

TypeScript 角落 · 读懂 export、const、function

JavaScript 文件就是模块：export 标出其它文件可以 import 的内容。const 声明一个不可重新赋值的变量。TypeScript 是 JavaScript 加上类型 标注 —— 关于某个值具有什么形状的说明，在代码运行前被检查，然后被擦除。 同一个插件用 harness 自己的 TypeScript 风格写就是这样： 

export function apply(ctx: Context): void { ... }

把 ctx: Context 读作「ctx 是一个 Context」，把 : void 读作 「不返回任何东西」。当你快速浏览 harness 源码时，可以在心里删掉参数列表里冒号 之后的一切，仍然理解运行时行为。

想法 2 —— 上下文是服务的仓库

一个服务是一个长期存活的对象，它在上下文上占据一个稳定的键。工具 注册表占据 ctx.tools；会话存储占据 ctx.sessions；subagent 运行时占据 ctx.subagents。任何插件随后都可以按键取用某项能力， 无需 import（甚至无需知道）实现它的那个包：

正是这种间接性让提供者可以替换。文件系统服务、shell 服务、 subagent 提供者 —— 每一个都是「在这个键下注册的那个东西」。把这些键指向一个远程 沙箱实现，整个产品就搬到了那里，无需修改任何调用方。harness 架构文档把这种可替换的能力称为接缝（seam） （docs/architecture.md，「Capability seams」）。

在 inject 中列出服务名的插件只是等待 —— Cordis 让它保持挂起，直到每个 被点名的服务都存在，然后激活它。如果某个服务后来消失（它的提供者被卸载）， 依赖它的插件会被停用。加载顺序变成框架计算出来的属性，而不是 你手工排序的东西。这也是你的第一根调试杠杆：一个「从未运行」的插件， 通常是在等待一个没人提供的服务，而 harness 会如实报告这一点 （「N row(s) did not activate: waiting for <service>」—— 你会在第 6 章的校验 步骤遇到这条消息）。

TypeScript 角落 · 数组与字符串

['tools', 'systemPrompt'] 是一个字符串数组字面量。TypeScript 推断它的类型为 string[]（「字符串数组」）。你还会看到 readonly string[] —— 同一回事， 但编译器禁止修改它。这两种标注在运行时都不存在。

想法 4 —— 类型化事件与四种派发模式

服务暴露方法用于直接调用（「启动一个 subagent」），也暴露事件用于 拦截与观察（「某个工具即将执行」）。插件用 ctx.on(name, listener) 监听。Cordis 事件的不同寻常之处在于：每个事件都声明了一个 派发模式 —— 它公开契约的一部分：

  • emit —— 发后即忘的观察。例如 session/event，这条「消防水带」 会宣告每一条被追加的会话日志事件。监听者可以看，但改变不了任何东西。
  • waterfall —— 环绕式中间件。每个监听者收到参数外加一个 next 函数，并包裹链条的其余部分。策略就是这样写的：工具 流水线的 tools/pre-execute 是一个 waterfall，监听者可以在其中允许、拒绝、延迟或 改写一次工具调用。
  • parallel / serial —— 被 await 的扇出，并行执行或按顺序执行。
那条人人都会踩的 waterfall 规则

waterfall 监听者必须调用并返回 next() 才算委派下去。不返回它就会把 链条短路 —— 当某个策略本就拥有这个决定权时这是刻意的，而当你只是忘了时就是灾难。 harness 的约定用粗体写明了这一点 （AGENTS.md：「Waterfall listeners MUST call next()」）。在 tools/pre-execute 上 漏掉 next() 会静默地阻塞进程里的每一个工具。现在就把它记牢；如果你 要构建第 13 章的延迟插件，它会很重要。 

ctx.on('some/waterfall', (payload, next) => {
  // observe or annotate payload here ...
  return next()            // ← the load-bearing line
})
TypeScript 角落 · 箭头函数与回调

(payload, next) => { ... } 是一个箭头函数 —— 一种紧凑的匿名函数。 JavaScript 像传递值一样传递函数，所以「注册一个监听者」字面上就是「把这个 函数交给 ctx.on，稍后调用它」。函数前的 async 让它返回一个 promise（一个稍后才会到达的值）；在它内部，await expr 会暂停直到 expr 落定。你会在每个工具定义里看到 async execute(args, exec) { ... await ... }。

想法 5 —— 注册是可撤销的副作用

这个问题决定了一个可热重载系统的成败：当插件卸载时，框架如何 撤销它做过的一切？Cordis 的答案：每一份贡献都经由上下文， 并且每一份都返回（或被包在）一个清理器（disposer） —— 一个清理函数。注册与 清理是同一个动作：

因为一切都遵守这条纪律，harness 可以在会话运行期间热重载插件、preset 或 你 profile 的 patch 文件，而不会有任何泄漏。仓库把这条约定定为 硬规则：「Registrations are effects: every contribution goes through ctx.effect() / ctx.on(); a registry's register() returns the disposer」 （$HOME/src/deepseek-harness/AGENTS.md，Conventions）。

组合：插件由 YAML 挂载

到目前为止都是孤立的插件。谁来决定哪些插件运行？在这个 harness 里：是配置文件， 不是代码。cordis.yml 是一列行，每行点名一个插件包及其 配置。下面是随包携带的监督者所基于的 standard preset 里的两行真实内容：

如何读一行：

  • id —— 该行的稳定地址。patch（下一章）按 id 定位行。
  • name —— 被挂载插件的 npm 包名。
  • config —— 传给该插件，并按它的 schema 校验。非法配置会在挂载时大声失败。
  • disabled: !!js … —— 唯一允许可执行表达式的地方：!!js 让一行 随环境切换（此处：在 Windows 上跳过 bash）。文件里其它一切都是字面数据。
  • {{model}} —— 模板变量，某些插件（如人格）会按本 agent 的路由解析它。 0.2.1 起 loop 只注册 provider 与 model；工作目录由必需的 working-directory 运行时上下文注入，不要在人格里写 {{cwd}} —— 未注册的变量会在装配期直接报错（第 7 章遇到的就是这个）。

这是关于 harness 最需要理解的一点：改变一个 agent 能做什么，就是改变为它组合了 哪些行。不是修改核心代码 —— 而是编辑一份列表。随 Creator mode 一起提供的 editing-cordis-compositions skill 开头正是这句话 （apps/cli/config/agent-presets/cordis/skills/editing-cordis-compositions/SKILL.md）。

分组与 isolate 领域（冲突规则的预告）

还有一个组合构造你会在第 6 章检视：行可以嵌套进一个分组，而分组可以携带一个 isolate 领域。原因：有些插件提供一项服务，而一个服务键在每个领域里 只能注册一次。如果某个 preset 行把服务提供到全局领域里，那么第二个会话挂载该 preset 时就会与第一个冲突。因此，拥有服务的 preset 会把提供者与其消费者一起包进一个带 isolate: {thatService: true} 的分组，让每个会话得到一份私有实例。standard preset 就为它的 工作流引擎这样做了：

本课程里你不需要设计领域 —— 随包携带的 preset 保留了从 standard 继承来的正确分组。 但你必须认得这个模式，因为出问题时挂载校验器会点名它（「a preset service must sit behind an isolate realm or move to the host composition」），而第 6 章会验证两个会话的挂载不会发生领域冲突。

自检理解（不需要机器）
  1. 某插件的 apply 从未运行，挂载报告说「waiting for schedule.」 哪里出了问题，为什么这不是该插件的 bug？（它声明了 inject: ['schedule']，而组合里没有任何东西提供那个服务 —— 修法是改组合，不是改代码。）
  2. 一个 tools/pre-execute 监听者记录每一次调用，然后什么都不返回。什么会坏？ （进程里的每一次工具调用都会静默停止 —— 该监听者因为没有返回 next() 而短路了 waterfall。）
  3. 为什么提供服务的 preset 行需要一个 isolate 领域？ （一个服务在每个领域只能注册一次；两个挂载该 preset 的会话会在 全局领域里冲突。）
