故障排查与参考

这门课让你做的每件事，出问题时的清单都在这儿；还有它依赖过的每个术语的词汇表， 以及一份值得你下个周末去读的 harness 文档地图。

故障清单

preset 的问题（第 6–7 章）

症状可能的原因 → 修法
preset 在挑选器里找不到bundle patch 里没有 preset-main-agent 声明行（或该行 import 失败）：0.2.x 起 $DSH_HOME/.agent-presets/ 目录不再被读取，所以先别去翻那个目录。先在 profile 的组合配置里找这一行 —— dsh --profile <名字> --dump-config | grep -A4 'id: preset-main-agent'；声明行本身在 presets/main-agent.patch.yml（由 scripts/sync-preset-patch.mjs 生成，tests/preset-patch.test.mjs 校同步），它必须存在、name: 为 @deepseek-ai/dsh-agent-preset、且没有 disabled:。然后用 agentPresets.list()（在 Creator 模式里）看 roster 实际注册了什么。如果那一行在、但启动日志里写着 failed to import，说明宿主没带这个包；如果写着 pending (waiting for service: agentPresets)，说明这个 profile 没有提供 registry 的 app（dsh web 提供）。
挑选器只显示裸 id，没有描述声明行里的 config.name / config.description 缺失或为空 —— 第 6 章第 2 步。（preset.yml 只喂给更老 dsh 的那份兼容副本。）
standingKeyFor：invalid config: $.persona … 或类似错误具名行下面的 YAML 缩进有问题 —— 通常是 prefix: | 块（0.2.x 的 dsh-persona 必填 prefix，旧字段 text 会让整行加载失败）。校验源文件并重跑生成脚本： python3 -c "import yaml,sys; yaml.safe_load(open('$HOME/src/dsh-supervisor/agent-presets/main-agent/agent.cordis.yml'))"，然后 npm run sync-preset。
N row(s) did not activate: waiting for <service>消费方行处在错误的领域里，或者那个宿主服务确实没被挂载（比如你在第 8 章之前就引用了 schedule）。
published process-global service(s) […]你在 preset 里随手加了一个 provider 行。把 provider 和消费方包进同一个 isolate 组，或者把它挪到宿主一侧。（第 2–3 章。）
用这个 preset 开第二个会话失败；第一个却没事还是领域（realm）那个 bug —— 冲突在第二次挂载时才触发。修法同上。
工具列表里没有 subagentworker 模型白名单是空的（派生被有意关掉了）、受保护的那一行落到了委派组的 config: 列表之外，或者文件没保存。加一条被允许的路由，然后重新校验。
worker 表现得像普通写码助手（不 report、没有 outcome.md）那一行的 persona: 没生效（缩进问题），或者你的 spawn 提示词漏了协议 —— 到子级会话视图里看这次工具调用用的 persona。

profile patch 的问题（第 8、13 章）

症状可能的原因 → 修法
改了 patch，却什么都没变盯着 dsh web 的日志看有没有 hmr/config-update-failed —— 解析出错时会沿用上一棵好树。重复的行 id 是致命的；“空”文件必须写成 []。
第 8 章之后 schedule_create 还是未知工具行名拼错了，或者你改错了文件。dsh --profile web --dump-config | grep -n schedule 能一锤定音。
bundle 插件（第 13 章）一直没挂载bundle 列表是启动期的事 —— 你重启过一次了吗？这个包在 dependencies 和 dsh.profile.bundles 里都列了吗？它的 manifest 里带 dsh.bundle.patch 吗？
你改完之后整棵树在启动时就挂了恢复备份：cp $HOME/.dsh/profiles/web/cordis.patch.yml{.bak,}，然后重启。第 4 章让你做备份就是为了这个。

动态插件的问题（第 5 章，以及第 11 章里那段历史练习）

症状可能的原因 → 修法
service "x" is not declared用了 ctx.x 却没声明 inject。改用 ctx.get('x') 加一个 undefined 检查，或者声明这个硬依赖。
客户端那一半解析失败动态代码里用了 JSX / TypeScript / import。只能用纯 JS 和 React.createElement。
run 显示“成功”，但界面没出现渲染发生在 run 给出答复之后。cordis_inspect_self(pluginId, packageId) → renderFailure 里带着那一次 run 的崩溃信息。
一直停在 awaiting-approval那是在等你 —— 去对话里批准那张卡片。你拒绝之后，绝不要让 agent 再去重新申请。
重启后插件没了设计如此：它只在进程内存里。重新跑一遍它（授权会保留），或者把它打包（第 13 章）。
@pluginId 引用显示“unavailable”那是别的会话的插件、未定义，或者被重启弄丢了。不要默默重建 —— 工具集的提示词禁止这么做，是有正当理由的。

监督者行为的问题（第 7、10、12 章）

症状类别 → 修法
还没巡检已有脚本就开始一个目标协议违反 → 强化 GOAL SETUP，要求在 start_goal 之前先读持久状态和相关的 runbook/脚本。
在一个提问上永远卡住检查第 8 章那条耐心路径是否真的工作（提醒建了吗？schedule 挂上了吗？），然后强化 QUESTIONS 的措辞。
worker 调用 ask_user_question 然后默默干等spawn 策略回归：受保护的请求必须禁掉那个工具；report 仍是唯一的向上提问通道。
每次定时器唤醒都重复一句“还在运行”协议违反：running 只表示驱动还开着。要比对具体证据；第一次检查发现没变化就做一次探针，下一次仍然没变化就 interrupt 并恢复/重新派生。
每次定时器唤醒都去纠偏健康的 worker协议缺口 → 把“新证据”定义清楚，并规定：只记录检查点，不做无谓的纠偏。
该纠偏的地方却直接终止人格问题：缺少“只有在当前回合必须立刻停止时才先用 interrupt_agent”这一句 —— 把它挪到 steer 规则旁边；模型是就近读的。
worker 派生时拒绝了推理强度所选的那个模型没有公示该路由配置的固定推理强度。在模型那一行改选目录里支持的值，或选 provider/default；插件从不做截断。
一次失败的请求之后，收敛通知很笼统原生重试期间，中间失败是有意保持沉默的。只有重试彻底耗尽后的最终错误才会带上 Terminal failure [CODE]；重试成功则正常收敛。
原生的停止方块“按了没用”它只中止一个回合，不管 worker，也不管持久提醒。要用监督动态 Feed 里的 ■ Full stop；它会递归停掉被委派的 worker、在 agent 空闲后删掉提醒，并把停止折叠持久化。
CHANGELOG 有断档把记录熔进每个动作的句子里（“Steer = send_message + 一行 CHANGELOG，永远一起出现”）。
重启之后它又开始重新盘问它没去查 .agi/ 和目标状态 —— 确认 GOAL.md 是否存在、目标工具里有没有这个目标；如果都有，就强化 STATE 那句“重启不该有任何代价”。
已经做完的工作又派生了重复的 workeroutcome 纪律：分诊收敛通知时必须先读 outcome.md 再规划；把第 4 步的第一条写明确。

术语表

术语含义（章节）
插件带 name/inject/apply(ctx) 的对象，被挂载进树里（2）。
服务挂在稳定的 ctx.<key> 上的长生命周期能力（2）。
inject声明出来的硬依赖；插件会等到它们存在才生效（2）。
waterfall环绕中间件式的事件；监听器必须返回 next() 才算委托下去（2）。
Effect / disposer可撤销的注册；返回的那个函数就是用来撤销它的（2）。
Row（行）cordis.yml 里的一条条目：id + 包名 + config（2）。
Profile / bundle / patch 层挑选 bundle 的目录；可分发的行栈；按 id 定位、按顺序叠加的覆盖（3）。
宿主平面 vs. agent preset进程共享的行 vs. 某一个会话自己的行（3）。
isolate 领域按组划分的服务命名空间，用来避免 preset 之间的冲突（2、6）。
Rosterctx.agentPresets：列出/复制/校验 preset（3、6）。
会话 / 回合 / 步骤持久事件日志 / 一次“从唤醒到静止”的单位 / 一次模型请求连同它的工具调用（3）。
收件箱（Inbox）agent 收到的回合排成的 FIFO；监督者对一个正在运行的直接子级做纠偏时，是有意让它到下一次模型步骤才接上（3、9）。
可续用的子代理（continuable subagent）持久的子会话，跨重启也能给它发消息、能把它恢复起来（9）。
驻留期（activation）子 agent 驻留在内存里的那段时间（9）。
收敛通知子级的驻留期结束时，无条件发给父会话的通知（9）。
report子级发给父级的消息工具；默认以唤醒方式投递（9）。
插件 / 包 / Run（动态）稳定的 id / 不可变的代码版本 / 一次性的激活尝试（5）。
槽位（slot）具名的 UI 座位，客户端插件把 React 组件注册进去（11）。

你在哪儿，接下来是什么

你用一份自己写的 preset、一段协议文字、一行 schedule、几个窄口径的打包策略/UI 插件， 以及一套文件约定，搭出了一个常驻的监督者 —— 而且它站着的每一个机制你都能讲清楚：插件树、 两个平面、收件箱、可续用的子级、收敛通知。那份理解才是 持久的产物；监督者只是它的第一个证明。

顺理成章的下一步，大致按野心从小到大：

  • 提高并行上限 —— 人格里“一次一个 worker”的规则只是一句话；机器本身 已经能处理很多子级（交织出现的收敛通知之类都不在话下）。试试两个。
  • 按任务给 worker 更丰富的能力 —— spawn 那一行支持 在设置里批准一条能看图的路由，于是它可以去看截图；而固定的监督者 过滤器会让 ask_user_question 进不了任何 worker。
  • 跑真实任务 —— 非阻塞的目标设置可以放大到“把这个 X.com 账号做起来”； 只有当现有工作区的配置无法安全地提供凭证时，它才会开口要凭证。
  • 自我演化（设计 §3.4） —— 让监督者以提问的形式提出人格改动， 由你来应用。日常聊天仍然是纠偏和停止的操作面。
  • 回馈上游 —— 你发现了那个过期的 skill（第 5 章）。这个仓库接受 issue 和 discussion；CONTRIBUTING.md 很短。
